# Sprint 8 — Tool registry

## S08-08 — The tool execution context (S08-08).

### What changed
A minimal, tenant-scoped, immutable [`ToolExecutionContext`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/ToolExecutionContext.java) (`toolexecution.domain`) — the <em>call context</em> a tool is executed with. It carries exactly the slice a tool adapter must see and nothing that must not: the verified `tenantId`, the verified `actor`, the `runId` / `stepRunId` the call belongs to, the `correlationId` for tracing, and the `capabilities` (the minimal permission scopes the caller holds — read by the invocation permission guard, S08-09). It holds <b>no secret</b> — no JWT, API key, token, full prompt or document — which is the S08-08 rule ("do not hand out secrets to every tool adapter"). It is built <em>server-side</em> from the verified security context (HTTP) or the stored run re-checked against PostgreSQL (worker) — never from the Planner's arguments — and is an immutable value: the `capabilities` set is stored as an unmodifiable defensive copy and there are no mutators, so a model argument can never swap the actor or tenant the call runs as (the S08-08 acceptance). Canonical-constructor validation rejects a null tenant, run or capability set — the tenant is mandatory, a context with no tenant cannot scope a call (invariant 1) — while the actor, step and correlation label may be null (the correlation label defaults to the run at the wiring layer, per `CorrelationHeaders`). It reads no time, no randomness, no Spring or I/O, and depends on <em>no other module</em> (so the module boundary is unchanged: `toolexecution` still compiles only against `agentcatalog`, `audit` and `workflowexecution`). It is the calculator-layer mirror of `TenantContext` (`identity.application`), decomposed into its `tenantId` / `actor` primitives because `toolexecution` may not compile-depend on `identity` (the architecture gate, S02-08).

### Why
`BuiltInTools` seeds read-only tool descriptors (S08-02) and the pure executors exist (S08-05/06/07), but nothing yet threads the "who is calling, within what" context to a tool. The plan task ("pass tenant, actor, run, step, correlation ID and minimal capabilities; do not hand out secrets to every tool adapter") needs a single, explicit value for that — and the acceptance ("model arguments cannot replace the actor/tenant context") is a property of an immutable, server-side-built, validated value, not of prose. `ToolExecutionContext` is that value: it is the boundary the executor draws between the trusted security context (which decides who the call runs as) and the tool adapter (which must only see the minimal slice). It is placed in `domain` because it is a pure value (no Spring/I/O, reads neither time nor randomness, invariant 10), matching `ToolDescriptor` and the other `toolexecution.domain` values, and it is listed as a permitted public type of `toolexecution` in `docs/architecture/module-api.md` for the later `ToolExecutionService` / `StepHandler` wiring (S08-09 onward). The `capabilities` field is carried because the invocation permission guard (S08-09) re-checks scopes at call time; it is minimal — scope names only, never a token.

### Verification
Unit, DB-free, no model/Kafka/system clock, no module edges: `ToolExecutionContextTest` (9 tests) — all six fields round-trip; a null `tenantId`, `runId` or `capabilities` each throws `IllegalArgumentException` (with the field name in the message); an empty capability set is allowed and means no side effect; `actor`/`stepRunId`/`correlationId` may be null; the `capabilities` set is returned <em>unmodifiable</em> (a mutation attempt throws `UnsupportedOperationException`) and is defensively copied (mutating the source set after construction does not change the context); value equality holds for equal contexts and a different tenant breaks it; a reflection pass over the record components proves the field set is exactly `{tenantId, actor, runId, stepRunId, correlationId, capabilities}` and none is a secret-bearing name; and there is no mutator — the only way to change who a call runs as is a fresh, validated context, so the model cannot supplement the actor/tenant. `:apps:agentflow-app:check` green — compilation, unit, architecture gate (the change adds <em>no</em> new dependency edge — `toolexecution.domain.ToolExecutionContext` imports only `java.util` / `java.util.UUID`; the `PackageDependencyGraphTest` declared graph and the `ArchitectureBoundaryTest` ALLOW map both still hold), spotless formatting, and OpenAPI contract (the new domain value adds no controller, so the contract does not drift). The architecture gates ran active, confirmed from the JUnit XML (`ArchitectureBoundaryTest`: `tests=1, skipped=0, failures=0`; `NoCyclicModuleDependenciesTest`: `tests=1, skipped=0, failures=0`; `PackageDependencyGraphTest`: `tests=4, skipped=0, failures=0`) — so the gate is inert-free, not silently skipped.

## S08-09 — The invocation policy guard (S08-09).

### What changed
A re-check of the permission immediately <em>before</em> the call, not only at workflow activation, as the `toolexecution.application` `@Service` [`ToolInvocationPolicy`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/ToolInvocationPolicy.java): right before a tool runs it resolves the tool <em>through the registry</em> (`ToolRegistry#resolve` — which tool, its {@link ToolDescriptor#riskClass()} and {@link ToolDescriptor#requiredScopes()}), and then checks the caller's <em>current</em> permission set (`ToolExecutionContext#capabilities()`) holds <em>every</em> required scope. The decision is returned as the immutable value [`PermissionDecision`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/PermissionDecision.java) carrying the machine-readable {@link ToolExecutionOutcome} (`ALLOWED` / `DENIED`) and a stable {@code reason()} (`allowed` / `missing_scope` / `unknown_tool`) plus the ordered {@code missingScopes()} the executor classifies with — so classification and logging need no string parsing. A call is `ALLOWED` only when the tool resolves <em>and</em> the current scopes cover the required ones; an unknown tool, an absent scope, or a capability set that lacks the side-effect scope is `DENIED`, and the guard fails safe with a `null` context for a scoped tool (a read-only tool needs no scope, so an empty set is "no side effect permitted", not "everything denied").

Supporting values:
- `ToolExecutionOutcome` — the invocation vocabulary (`ALLOWED` / `DENIED` / `EXECUTED`).
- `PermissionDecision` — the immutable decision: `outcome()`, `toolName()`, `reason()`, and `missingScopes()` (unmodifiable — an external caller cannot silently widen a decision).

It reads no time, no randomness, no Spring/I/O beyond the registry it wraps, and <b>adds no new cross-module compile import</b> — it reads the catalogue's risk class through `ToolDescriptor#riskClass()` (the catalogue-owned value already carried into the descriptor by S08-01), and its only non-`toolexecution` reference to `agentcatalog.domain.ToolRiskClass` is a Javadoc `{@link}`, not a compile edge — so the module boundary is unchanged (`toolexecution` still compiles only against `agentcatalog`, `audit` and `workflowexecution`).

### Why
`ToolExecutionContext` (S08-08) threads the caller's capabilities to a tool, but nothing yet re-checks them at call time — the plan task ("check the permission immediately before the call, not at activation; if a permission revoked after activation, block the call") needs exactly that. The acceptance is a property of re-checking the <em>current</em> permission set, not of trusting a check captured at activation: a permission granted at activation can be revoked by the time the executor runs the step, and the model must not be able to smuggle a capability through a stale check (invariant 7 / ADR-006 — the model is never an authorization authority, so the permission check is decided server-side from the verified context). `ToolInvocationPolicy` is the value that closes the loop: the registry (S08-02) is the owner of *which tools are registered and with what risk/scope*, and the guard reads those attributes **through** the registry rather than re-declaring them; the caller's capabilities come from the server-side-built `ToolExecutionContext` (never from the Planner's arguments). It lives in `application` (with `ToolRegistry`) rather than `domain` because it is a `@Service` that holds the registry, not a pure value, and it is the counterpart of `identity.application` permission checks.

### Verification
Unit, DB-free, no model/Kafka/system clock, no module edges: `ToolInvocationPolicyTest` (12 tests) — a scoped tool is `ALLOWED` when the current capability set holds every required scope; `DENIED` with `reason() = missing_scope` when one required scope is absent (the absent scope is named in `missingScopes()`); an <em>extra</em> capability does not change an `ALLOWED` decision; an unknown tool is `DENIED` with `reason() = unknown_tool` even when the caller holds every scope; an empty capability set `ALLOW`s a read-only tool but `DENY`s a scoped one (empty = no side effect permitted, not everything denied); a `null` context `DENY`s a scoped tool while its read-only sibling stays `ALLOW`ed; and <strong>the acceptance</strong> — the same scoped tool is `ALLOW`ed while the caller holds the scope (the activation state) and `DENIED` with the full required scope set named in `missingScopes()` when the current set no longer holds it (a permission revoked after activation), proving the guard re-checks the <em>current</em> permissions each time and does not reuse a captured decision. Also: the decision value object carries an empty / unmodifiable `missingScopes()` set. `:apps:agentflow-app:check` green — compilation, unit, architecture gate (the change adds <em>no</em> new compile dependency edge — `ToolInvocationPolicy` imports only `toolexecution` and `java.util`/Spring; the only `agentcatalog.domain.ToolRiskClass` reference is a Javadoc `{@link}`, not a compile edge — so the `PackageDependencyGraphTest` declared graph and the `ArchitectureBoundaryTest` ALLOW map both still hold), spotless formatting, and OpenAPI contract (the new `application` service adds no controller, so the contract does not drift). The architecture gates ran active, confirmed from the JUnit XML (`ArchitectureBoundaryTest`: `tests=1, skipped=0, failures=0`; `NoCyclicModuleDependenciesTest`: `tests=1, skipped=0, failures=0`; `PackageDependencyGraphTest`: `tests=4, skipped=0, failures=0`) — so the gate is inert-free, not silently skipped.

## S08-07 — The deterministic ticket lookup (S08-07).

### What changed
A pure, dependency-free [`TicketLookup`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/TicketLookup.java) (`toolexecution.domain`) closing the demonstrative read-only `ticket.lookup`: it answers a ticket id against a fixed, in-memory fixture dataset (rows {@link TicketRecord#ticketId() TKT-1001 (open, $49.99), TKT-1002 (on hold, $129.00), TKT-1003 (closed, $42.50)}) and reproduces all three outcomes the plan asks for, without any external network: {@link TicketOutcome#NOT_FOUND} for an id absent from the fixture (answered deterministically, <em>before</em> any flap draw is consulted), {@link TicketOutcome#TRANSIENT_FAILURE} for a known ticket that flaps on every attempt (a transient fault, retried up to a bounded number of attempts so a retry can recover), and {@link TicketOutcome#SUCCESS} for the first clean attempt against a known ticket, returning the found {@link TicketRecord}. The one thing it reads — the per-attempt flap draw — is <em>injected</em> as a {@link java.util.function.Supplier<Double>} in {@code [0, 1)} (the same injection seam {@link RetryPolicy} uses for its jitter), so a fixed draw makes every outcome reproducible and the no-seam {@link #lookup(String)} entry point uses a shared {@link java.util.SplittableRandom} for realistic flapping in production. Its output is {@link TicketResult}; its fixture rows are {@link TicketRecord}, and the two closed vocabularies are {@link TicketStatus} (OPEN/ON_HOLD/CLOSED) and {@link TicketOutcome} (the three outcome classes). It reads no time, no system randomness, no Spring or I/O — a pure, testable value (invariant 10). `BuiltInTools` seeds the read-only `ticket` descriptor (id `tool-ticket-lookup-1`, strict input/output JSON Schemas, {@code READ_ONLY}, a 5 s timeout, the default retry policy) and the registry seeds it at startup.

### Why
`BuiltInTools` already seeded a read-only `ticket` descriptor (S08-02); its behaviour was unspecified. The plan task ("deterministic `ticket.lookup` tool, read-only, no external network, three outcomes: not found / success / transient failure") is deliberately demonstrative, so it needs a real, deterministic, dependency-free implementation — not a call out to a database or an external lookup service the demo could not reach. The injected flap draw is the same seam the retry policy uses, so the three outcomes are exactly what a read-only tool against an occasionally flaky backend looks like: a missing id is a deterministic answer (never flaps), a flapping backend is a transient failure a retry recovers, and the first clean attempt succeeds. As with S08-05 and S08-06, the executor that invokes `ticket` by name (permission check, timeout, output-schema validation) is built later (S08-08), so this task delivers the pure lookup and leaves the descriptor seeded by S08-02 untouched (re-registering it would be a duplicate that breaks startup).

### Verification
Unit, DB-free, no model/Kafka/system clock: `TicketLookupTest` (12 tests) — a known ticket answers {@link TicketOutcome#SUCCESS} with the found record on a clean attempt; a draw just below the {@link TicketLookup#FLAP_PROBABILITY} threshold flaps once then answers; a ticket that flaps on <em>every</em> attempt is a {@link TicketOutcome#TRANSIENT_FAILURE} after {@code maxAttempts} retries; a known ticket that flaps then clears succeeds after retries; an absent ticket is a deterministic {@link TicketOutcome#NOT_FOUND} with {@code attemptsUsed = 0} and no flap draw; the boundary draw ({@code FLAP_PROBABILITY - 1e-9} succeeds, {@code 0.0} succeeds, {@code FLAP_PROBABILITY} flaps); the outcome is deterministic for the same inputs; the production default entry point never throws for known or unknown ids; and every input guard throws {@link IllegalArgumentException} (blank id, {@code null} source, {@code maxAttempts < 1}, an out-of-range draw outside {@code [0, 1)}). `:apps:agentflow-app:check` green — compilation, unit, architecture gate (the change adds no new dependency edge — `toolexecution` already depends on `agentcatalog` for `ToolRiskClass`), spotless formatting, and OpenAPI contract (the new `domain` values add no controller, so the contract does not drift). The architecture gates ran active, confirmed from the JUnit XML (`ArchitectureBoundaryTest`: `tests=1, skipped=0, failures=0`; `NoCyclicModuleDependenciesTest`: `tests=1, skipped=0, failures=0`; `PackageDependencyGraphTest`: `tests=4, skipped=0, failures=0`) — so the gate is inert-free, not silently skipped.

## S08-06 — The report formatter (S08-06).

### What changed
A pure, dependency-free [`ReportFormatter`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/ReportFormatter.java) (`toolexecution.domain`) closing the concrete `report.format`: it takes structured {@link StructuredFact}s and their {@link Citation}s and renders them into an HTML-escaped {@link ReportFormat#MARKDOWN} or {@link ReportFormat#JSON} report. Every dynamic value (fact text and every citation source/url) is HTML-escaped <em>both</em> formats, so a hostile or prompt-injected fact (documents and tool outputs are untrusted content, invariant 7) can never turn the report into executable markup (`<script>` → `&lt;script&gt;`). The report is capped at {@code 4000} characters: facts are included <em>whole</em> (never cut mid-fact) and the rest are dropped, marked {@link ReportResult#truncated()} — this is what keeps the output schema stable for empty, valid and oversized inputs (the S08-06 acceptance). Holds its input as {@link ReportRequest} and its output as {@link ReportResult}; a {@code null} facts list is normalised to empty at construction, a {@code null} fact entry is skipped, and a {@code null} format defaults to {@link ReportFormat#MARKDOWN}, so none of them throws. It reads no time, no randomness, no Spring or I/O — a pure, testable value (invariant 10). The supporting value objects are {@link ReportFormat} (`MARKDOWN`/`JSON`), {@link Citation} (`source`, `url`), {@link StructuredFact} (`text`, `citations`), {@link ReportRequest} and {@link ReportResult}.

### Why
`BuiltInTools` already seeded a read-only `report` descriptor (S08-02); its behaviour was unspecified. The plan task ("format structured facts and citations into a Markdown or JSON report; no executable HTML; limit result length; stable schema for empty, valid and oversized inputs") needs a real, deterministic, dependency-free renderer — not a call out to a markup/HTML library that could emit executable HTML. Escaping is the smallest implementation that closes the loop and adds no escape surface, and whole-fact truncation is the only scheme that keeps a Markdown line and a JSON object well-formed while bounding the result — so it is the right tool, not a general-purpose HTML renderer built only for novelty. As with S08-05, the executor that invokes `report` by name (permission check, timeout, output-schema validation) is built later (S08-08), so this task delivers the pure formatter and leaves the descriptor seeded by S08-02 untouched (re-registering it would be a duplicate that breaks startup).

### Verification
Unit, DB-free, no model/Kafka/system clock: `ReportFormatterTest` (19 tests) — empty, `null` facts and a `null` format all yield the same stable shape (JSON: `{"truncated":false,"factCount":0,"facts":[]}`; Markdown: `# Report\nNo facts to report.`), valid Markdown/JSON render facts and citations correctly (with a URL, with a {@code null} URL, a blank source skipped, a `null` entry skipped), `<script>` and `a & <b>` are HTML-escaped in both formats (no {@code <}/{@code >} in the output), and a 300-fact oversized input is truncated (whole facts dropped, {@code truncated=true}, {@code charCount ≤ 4000}) while keeping the same keys. `:apps:agentflow-app:check` green — compilation, unit, architecture gate (the change adds no new dependency edge), spotless formatting, and OpenAPI contract (the new `domain` values add no controller, so the contract does not drift).

## S08-05 — The safe calculator evaluator (S08-05).

### What changed
A pure, dependency-free [`Calculator`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/Calculator.java) (`toolexecution.domain`) closing the concrete `calculator.evaluate`: a self-contained recursive-descent operator-precedence parser over a closed numeric dialect (operands are typed {@link BigDecimal}s, exact and typed) built from {@code + - * /}, parentheses and decimal/scientific literals. It is an evaluator, never a general interpreter — no {@code eval}, no shell, no reflection, no class loading, no access to any language feature (invariant 7 / ADR-006). Addition, subtraction and multiplication are exact {@link BigDecimal} operations; division is bounded to 34 fractional digits half-up ({@code 1/3} deterministic, {@code 10/4} exact), a divide-by-zero throws, and every intermediate result is magnitude-bounded to {@code 1E1000} so growth turns into a deterministic {@code overflow}. The new {@link CalculationException} carries a stable {@code reason()} code (`invalid-token`, `empty-expression`, `division-by-zero`, `overflow`) — the calculator-layer counterpart of `SchemaValidationException`.

### Why
`BuiltInTools` already seeded a read-only `calculator` descriptor (S08-02); its behaviour was unspecified. The plan task ("safe calculator: safe parser") needs a real, deterministic, dependency-free evaluator — not a call out to an external `ScriptEngine`/`eval` (an invariant: an untrusted Planner is never a code interpreter). The recursive-descent parser is the smallest implementation that closes the loop and adds no escape surface, so it is the right tool, not a general-purpose expression engine built only for novelty.

### Verification
Unit, DB-free, no model/Kafka/system clock: `CalculatorTest` (29 tests) — operator precedence ({@code 2 + 3 * 4 == 14}), nested parentheses, unary signs ({@code -(-5)}), exact and scientific literals ({@code 1.5E2 + 1 == 151}), division exactness ({@code 10/4}) and rounding ({@code 1/3}), division-by-zero ({@code "(2 - 2)"}) and direct zero, overflow ({@code 1E600 * 1E600}), and every malformed-input reason — all assertions pass. A stray operator / unbalanced parenthesis throws {@code invalid-token} (not {@code IndexOutOfBoundsException}); the `seenDot` fix parses decimals and exponents correctly. `:apps:agentflow-app:check` green (unit + architecture gates + spotless + OpenAPI).

## S08-04 — Output-schema validation (S08-04).

### What changed
The very same dependency-free [`SchemaValidator`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/SchemaValidator.java) (`toolexecution.domain`) now serves its second role: it validates the tool's <em>result</em> against its machine-readable {@link ToolDescriptor#outputSchema()} (the same {@link JsonSchema} draft 2020-12 root) <em>after</em> the tool runs and <em>before</em> the step is marked SUCCEEDED — so a result that does not conform to the contract is never accepted, forwarded to the next step, or checkpointed. The engine is schema-agnostic (it validates any parsed value against any parsed schema), so the input (S08-03) and output (S08-04) gates share one implementation, one {@link SchemaValidationException}, and one set of protective payload limits, a maximum node count and a maximum nesting depth. It distinguishes a <b>schema mismatch</b> — a produced result that fails the output schema, a deterministic contract failure — from a <b>transient execution error</b> the tool itself raises before producing a result: the output gate only runs on a produced result, so a transient failure short-circuits on the tool call and is classified separately by the retry classifier. On the first violation it throws a [`SchemaValidationException`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/SchemaValidationException.java) with the same stable `reason()` code (`type-mismatch`, `missing-required`, `unknown-property`, `payload-too-large`, `payload-too-deep`) the S08-03 engine uses. It reads no time, no randomness, no Spring or I/O — a pure, testable value (invariant 10). The class/method Javadoc of `SchemaValidator` and `SchemaValidationException` is updated to describe both roles.

### Why
The S08-04 plan task ("validate tool result before passing to the next step; limit size; distinguish schema mismatch and transient execution error") had no implementation yet. It closes the acceptance criterion: an invalid output is not marked as a successful step result. The engine already closed S08-03 with the very same code — the input gate validates {@code ToolDescriptor#inputSchema()} before the call — so the output gate reuses it rather than duplicating a schema engine (nothing a full schema engine would add only for novelty). The after-call gate belongs, conceptually, to the tool executor (the `TOOL_CALL` {@code StepHandler} / {@code ToolExecutionService} listed as the `toolexecution` public service in `docs/architecture/module-api.md`): the handler resolves the descriptor's {@code outputSchema}, validates the parsed result, and only returns {@code StepResult.succeeded(result)} when it conforms. That executor does not exist yet (built in S08-05–S08-08), so — exactly as S08-03 delivered the engine and documented the before-call gate for the executor to apply — S08-04 delivers the engine's output role, proves it, and documents the after-call gate for the later handler. The distinction from a transient error is inherent: the engine only runs on a produced result, and a transient tool failure (a provider timeout, a thrown error) never reaches it, so the two failures are different exception types the executor classifies differently.

### Verification
- Unit, DB-free, no model/Kafka/system clock: `SchemaValidatorTest` (27 tests — 6 new for S08-04) — a tool result matching its output schema is accepted; a type-mismatch, a missing required field and an unknown property (strict output contract) and an oversized result are all rejected with `type-mismatch` / `missing-required` / `unknown-property` / `payload-too-large` <em>before the step is marked succeeded</em> (the acceptance criterion, asserted via an {@code OutputResultGate} harness that runs the tool, validates the result, and only records SUCCEEDED on a conforming result); a tool that fails transiently (throws before producing a result) is reported as a transient error (`IllegalStateException`) and <em>not</em> a `SchemaValidationException`, proving the schema-mismatch / transient-error distinction.
- `:apps:agentflow-app:check` green — compilation, unit, architecture gate (package/module — the change adds no new dependency edge), spotless formatting (fixed with `spotlessApply`), and OpenAPI contract (`OpenApiContractCheckTest`); the new `domain` value adds no controller, so the contract does not drift. The architecture gates ran active, confirmed from the JUnit XML (`ArchitectureBoundaryTest`: `tests=1, skipped=0, failures=0`; `NoCyclicModuleDependenciesTest`: `tests=1, skipped=0, failures=0`; `PackageDependencyGraphTest`: `tests=4, skipped=0, failures=0`) — so the gate is inert-free, not silently skipped.

## S08-03 — Input-schema validation (S08-03).

### What changed
A pure, dependency-free [`SchemaValidator`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/SchemaValidator.java) (`toolexecution.domain`) that validates a parsed JSON value — the tool-call arguments — against the tool's machine-readable {@link ToolDescriptor#inputSchema()} (a {@link JsonSchema} draft 2020-12 root held as an immutable `Map` tree), so an invalid payload is blocked <em>before any tool side effect</em>. It is bound to a schema with `SchemaValidator.of(JsonSchema)` and injectable limits (defaults `DEFAULT_MAX_NODES = 1_000`, `DEFAULT_MAX_DEPTH = 20`). It validates the subset of JSON Schema a tool call needs: {@code type} matching for every JSON value type (object, string, integer, number, boolean, array, null — an {@code integer} schema accepts an integral value, including an integral double such as {@code 2.0}, but not a fractional {@code 2.5} or the string {@code "5"}), {@code required} fields, {@code properties} typing, {@code items} typing for arrays, and {@code additionalProperties: false} (the "strict contract" that rejects unknown properties; the default — absent or `true` — allows them), plus two protective payload limits, a maximum node count and a maximum nesting depth. On the first violation it throws a [`SchemaValidationException`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/SchemaValidationException.java) carrying a stable {@code reason()} code (`type-mismatch`, `missing-required`, `unknown-property`, `payload-too-large`, `payload-too-deep`) so the executor can classify the failure without parsing the message. It reads no time, no randomness, no Spring or I/O — it walks the already-parsed `Map`/`List` tree exactly as `JsonSchema` holds its schema as a parsed tree — so it is a pure, testable value.

### Why
The S08-03 plan task ("validate types and required fields before the call; limit payload size/depth; in strict contracts reject unknown properties") had no implementation yet. This closes the acceptance criterion: an invalid payload is blocked before any side effect. It lives in `domain` (not `application`) because schema validation is a pure, dependency-free value that reads neither time nor randomness (invariant 10), so it is testable in isolation and has no I/O; `JsonSchema` and `ToolDescriptor` already live in `domain`, and `ToolDescriptor.inputSchema()` is exactly what `SchemaValidator` validates against. The registry (S08-02) is what hands `SchemaValidator` its schema — the planner/permission layers read a tool's schema **through** the descriptor — so validation stays close to the contract it validates, without coupling to the application port. The stable `reason()` is deliberate: the tool executor classifies the failure (S08-13) without string parsing.

### Verification

## S08-02 — The deterministic tool registry (S08-02).

### What changed
An in-memory, deterministic [`ToolRegistry`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/ToolRegistry.java) (`toolexecution.application`), the single source of *which tools are registered*. The platform registers the built-in tool descriptors once at startup (via the `toolRegistry` `@Bean`, `config/ToolRegistryConfiguration.java`); the Planner chooses a tool **through** it and every permission check reads a tool's risk class and required scopes **through** it. A tool is therefore never callable unless it is registered.

Built around:
- `ToolRegistry` — `register(descriptor)`, `resolve(name, version)` → `Optional<ToolDescriptor>` (empty for an unknown pair), `containsTool`, `all()` (unmodifiable snapshot), `size`. Thread-safe (`ConcurrentMap`, atomic `putIfAbsent`). Holds descriptors **only** (metadata); the executors are registered separately by name in S08-05/S08-06/S08-08.
- `ToolKey` — the package-private `(name, version)` value key (record). The dedup key is the pair the Planner references, **not** the descriptor `id` (which stays a stable unique identifier on the descriptor for audit/persistence).
- `DuplicateToolRegistrationException` — extends `IllegalStateException`; a startup/config error, thrown by `register` on a duplicate `(name, version)`.
- `BuiltInTools` — the factory that seeds `calculator` (S08-05) and `report` (S08-06) descriptors at startup.

### Why
The S08-02 plan task ("register adapters at startup; reject duplicate ID/version; forbid dynamic registration by the LLM/user; deterministic registry") had no implementation yet. This closes the acceptance criteria:
- **Unknown tool is never called.** `resolve` returns `Optional.empty()` for any pair never registered; the planner/permission layers treat that as "not callable", so an unknown or never-registered tool cannot be invoked.
- **Duplicate registration clearly breaks startup.** A duplicate `(name, version)` throws `DuplicateToolRegistrationException` *from the `@Bean` factory method*, so the Spring context fails to start — a mis-wired registry is a configuration error that is visible, not silently kept (one of two tools).
- **No dynamic registration by the LLM/user.** There is **no HTTP endpoint**; registration is a platform operation at startup only, an invariant (`AGENTS.md` "Forbidden": dynamic tool registration by the LLM or a user).
- **Recovery.** The registry is in-memory with no external dependency (no DB), so it is safe in every profile (API role, DB-less skeleton). It holds no secrets, no prompt, no `tenantId`/`runId`; its `all()` snapshot is metric/log-safe.

### Verification
- Unit, DB-free, no model/Kafka/system clock: `ToolRegistryTest` (7 tests) — resolve by `(name, version)`; unknown **name** / wrong **version** / blank **version** all resolve empty (unknown → never called); duplicate `(name, version)` rejected (first descriptor still stands); two distinct versions are distinct tools; `all()` is an unmodifiable snapshot; `null` descriptor rejected; 16 threads registering concurrent distinct keys do not lose entries (and concurrent `resolve` never throws).
- Lightweight Spring-context test (no server, no DB, no Kafka): `ToolRegistryStartupTest` — the real `ToolRegistryConfiguration` boots the context seeded with the built-in tools and resolves them while an unknown one resolves empty; a duplicate registration from the `@Bean` factory fails context startup with `DuplicateToolRegistrationException` as the root cause.

## S08-01 — The registered-tool contract (S08-01).


- **The registered-tool contract (S08-01).** The shape of a *registered tool* is now a typed, immutable value object, `ToolDescriptor`, in `toolexecution.domain` — the value that closes the loop between the tool allowlist (which tool/permission a run is allowed to use) and the executor (which runs it and how). A tool is only callable when it has a {@link ToolDescriptor#riskClass()} the caller is permitted to use, the caller holds every {@link ToolDescriptor#requiredScopes()} scope, and the call passes the {@link ToolDescriptor#inputSchema()} / {@link ToolDescriptor#outputSchema()} validation — none of which is inferred from the human-readable {@link ToolDescriptor#description()}. The `ToolDescriptor` is a `record` with value equality, so the registry can dedupe and cache it (S08-02), and its canonical-constructor validation guarantees an invalid descriptor can never reach a call (non-blank `id`/`name`/`version`, present schemas, present scopes/risk/retry, a strictly positive timeout).

- **`ToolRiskClass` — the tool's blast radius, owned by the catalogue.** The three-class enum (`READ_ONLY`, `WRITE`, `EXTERNAL_SIDE_EFFECT`) that classifies a tool by the change it can make to external state now lives in `agentcatalog.domain`, not `toolexecution.domain`. The catalogue is the *owner* of the tool allowlist and its risk taxonomy (module-map edge 3 / `docs/architecture/module-api.md`); keeping the risk model there is what lets the catalogue own "which tools exist and how risky they are" while `toolexecution` only *reads* a risk class the catalogue assigned. `toolexecution` depends on `agentcatalog` (edge 3) to carry `ToolRiskClass` into the `ToolDescriptor`, so the model is defined once, owned once, and never duplicated across the boundary. An unknown risk class is denied by default (`S11-01`, ADR-006): the executor trusts the catalogue's closed set, not the Planner.

- **`JsonSchema` — the machine-readable contract, held as an immutable value.** A tool's `inputSchema`/`outputSchema` are held as an immutable, dependency-free value `JsonSchema` (a `Map<String, Object>` root, defensively copied and made unmodifiable), not parsed or validated in the domain. The domain holds the *shape*; schema validation of call arguments happens at the application/persistence boundary (`S08-02`). It rejects a `null` root with `IllegalArgumentException` (a tool without a schema cannot be validated, so it is not registered) and is value-equal so two descriptors with identical schemas compare equal.

- **`RetryPolicy` — how a failed call is retried, owned by the executor.** The retry parameters (max attempts, base delay, multiplier, max delay, jitter) move to `toolexecution.domain.RetryPolicy` as the tool-layer's answer to "how do I retry a failed call" — the tool-level sibling of `workflowexecution.domain.RetryPolicy` (`S07-10`), which still drives a step's *workflow* retry. This is a value object (value equality, no dependencies), carrying the same reproducible, bounded backoff the workflow policy uses, plus the same injection seams so it is testable without the system clock or `Math.random` (invariant 10). It is owned by `toolexecution` because the tool registry decides a *tool's* retry policy; the workflow-level policy still lives in `workflowexecution`.

#### What changed
- `agentcatalog.domain.ToolRiskClass` (new) — the three-value enum (`READ_ONLY`, `WRITE`, `EXTERNAL_SIDE_EFFECT`); the blast-radius taxonomy owned by the catalogue.
- `agentcatalog.domain.ToolRiskClassTest` (new, unit, DB-free) — the enum has exactly the three canonical values and nothing else, and each risk class is reachable and named.
- `toolexecution.domain.RetryPolicy` (new) — the tool-level retry policy value object: value-equal, dependency-free, reproducible bounded backoff with injected jitter/time, `of(...)`/`ofDefaults()` factories, `delayMillisForAttempt(attemptsUsed)`, `isRetryAllowed`, `nextAttemptTime`, and value equality.
- `toolexecution.domain.RetryPolicyTest` (new, unit, DB-free) — the exponential backoff progression, the `maxDelay` cap, the constant-multiplier edge, jitter reproducibility over 6 × 500 real draws, `isRetryAllowed` bounded by `maxAttempts`, the out-of-range jitter rejection, `nextAttemptTime` from an injected instant, and every invalid-construction case.
- `toolexecution.domain.JsonSchema` (new) — an immutable value wrapping the JSON Schema draft 2020-12 root as a `Map<String, Object>`; defensive copy, unmodifiable root, `null` root rejected, value-equal.
- `toolexecution.domain.JsonSchemaTest` (new, unit, DB-free) — round-trip, unmodifiable root, mutation does not change the value, and `null` root rejection.
- `toolexecution.domain.ToolDescriptor` (new) — the registered-tool contract: the canonical `record` with validated constructor, the `of(...)` factory, `ofDefaults()`, and the non-mutating scopes copy.
- `toolexecution.domain.ToolDescriptorTest` (new, unit, DB-free) — the descriptor carries its schemas and risk class, refuses a blank identity / a null risk class / scopes / retry policy / non-positive timeout, a missing machine-readable schema is rejected, the allowed-scope set is copied (mutating the source set does not change the descriptor), and value equality holds.

#### Why
Before this task the only thing standing between the allowlist (S08-01's `toolexecution.tooling` work) and the executor was an implicit set of field names — nothing typed, validated, or shared, so the "which tools may a run use" decision could not be reasoned about or tested in isolation. `S08-01` makes that decision explicit as one contract. `ToolRiskClass` is owned by the catalogue because the catalogue owns the allowlist and its risk taxonomy (the module-map edge 3 boundary); moving the risk model into `agentcatalog` keeps it defined once, and `toolexecution` reads it through the permitted edge rather than re-declaring it. The description is deliberately *not* authorization: the Planner is an untrusted planner (ADR-006) that reads `description()` to pick a tool, but the permission check (`requiredScopes` + `riskClass`) is decided server-side from the verified permission context, and an empty scope set means "no side effect permitted regardless of the description" (invariant: the model is not an authorization authority). `JsonSchema` and `RetryPolicy` are held as immutable values (no schema-parsing or sleep in the domain) so they are comparable, cacheable, and testable with injected time and randomness (invariant 10), and the canonical-constructor validation keeps an invalid descriptor from ever reaching a call.
