# Sprint 8 — Tool registry

## S08-13 — The durable tool invocation history: which tool ran, how its call concluded, no secrets (S08-13).

### What changed
The plan asks for durable tool invocation metadata — tool ID/version, attempt, latency, outcome class, output reference — with sensitive values redacted and side-effect calls audited. The acceptance: an operator can determine WHICH tool executed and HOW its call concluded without seeing secrets. It is now in place end to end:

- **Migration `V3_3_17__create_tool_invocations.sql`** (owner `toolexecution`): an append-only `tool_invocations` table — `id`, `tenant_id`, `run_id`, `step_run_id` (nullable), `tool_name`, `tool_version`, `risk_class`, `attempt`, `outcome`, `latency_ms`, `output_reference`, `error_class`, `error_summary`, `created_at`. `run_id` is a plain value, not an FK (`workflow_runs` belongs to `workflowexecution` — a cross-module FK would couple the schemas); `tenant_id` lives on the row because toolexecution may not JOIN workflowexecution's tables. Redaction is **structural**: there are no columns for arguments, output payload, prompt or document (invariant 8) — nothing sensitive can be stored because there is nowhere to put it.
- **`ToolInvocationOutcome`** (`toolexecution.domain`): the closed vocabulary `SUCCEEDED` / `THROTTLED` (rejected under a concurrency cap, the call never started) / `TIMED_OUT` (ambiguous — the side effect may have completed, invariant 6 / ADR-003) / `FAULTED`. The executor decides the class, never the tool.
- **`ToolInvocationRecord`** (`toolexecution.domain`): the immutable row value; the canonical constructor validates tenant/run presence, non-blank `(name, version)`, 1-based attempt, non-negative latency; `recorded(...)` assigns the id (the `AuditEvent.created` convention). `output_reference` is a `step-run:<step-id>` pointer to the owning checkpoint — the payload keeps exactly one owner (`workflowexecution`, `workflow_step_runs.output_inline`).
- **`BoundedToolExecutor` gained the history seam**: an `execute(..., attempt)` overload (the 3-arg form reports attempt 1 — the retry loop of the future `TOOL_CALL` handler keys retries by it), an injectable monotonic `LongSupplier` for the latency measurement (invariant 10), and a report after every concluded call: success (with the output reference), throttle (stable reason, no reference — the call never started), ambiguous timeout (stable `tool_timeout`, no reference), and tool fault (`FAULTED` with a **redacted** token — the faulting type plus its stable reason code, bounded to 200 chars; the exception message can quote a secret, so it is never stored). A listener fault is logged and swallowed on purpose: history is observability, not business state, and a metadata write can never change what the caller observes.
- **`ToolInvocationListener`** (`toolexecution.application`): the `@FunctionalInterface` seam with a `NONE` no-op; **`ToolInvocationHistoryService`** is the `@Service` implementation — it appends the history row and, for every **started** call whose risk class is not `READ_ONLY`, an `audit_events` record: `AuditAction.INVOKE` / `AuditResourceType.TOOL`, actor `tool-executor` (the platform acts on the run's behalf — there is no human subject), redacted metadata `tool=<name>:<version>`. A read-only call changes nothing; a throttled call never started — neither is audited. `AuditEvent`/`AuditService` gained the 6-arg `created`/`record` overload carrying `metadataRedacted`; the existing 5-arg form delegates with `null`.
- **Wiring**: `ToolExecutionConfiguration.boundedToolExecutor` resolves the listener through an `ObjectProvider<ToolInvocationListener>` — the production context picks up the history service, a sliced context (the S08-10 `ApplicationContextRunner` test) falls back to `NONE`. `ToolInvocationRepository` is `@ConditionalOnBean(DataSource.class)` (S01-02): no database → the service fails loud → the executor degrades to a logged warning.
- **Tests**: 9 new cases in `BoundedToolExecutorTest` (success record with reference, injected-clock latency + attempt, throttle/timeout/fault records, redaction-never-message, listener-failure isolation, attempt guard); 6 in `ToolInvocationHistoryServiceTest` (read-only not audited, side-effect audited with identity, ambiguous timeout audited, throttled not audited, null record, fails loud without DB); 6 in `ToolInvocationRecordTest` (factory + every validation); a wiring test in `ToolExecutionConfigurationTest`; and `ToolInvocationRepositoryIT` on real PostgreSQL (round-trip, redacted fault tokens, append order across attempts, nullable fields, cross-tenant read isolation). `MigrationsTest` learns version `3.3.17`.

### Design decisions
- **Metadata by design, not scrubbing**: the cheapest redaction is the schema that cannot hold a secret. `error_summary` is a short stable token, never free text.
- **Timeout stays ambiguous in the history too**: `TIMED_OUT`, not `FAILED` — the row must not lie about a side effect the interrupt could not undo.
- **Audit only side-effect, only started**: the audit trail answers "what changed state", not "what was attempted".
- One lesson for the fallback skill: `ToolExecutionContext.stepRunId()` is a **String** (`step-1`, a run-model name), not a UUID — the table column and the record field are TEXT; the first compile assumed UUID and the IT schema disagreed.

`./gradlew clean check integrationTest` green — 760 unit tests (21 new) + 92 integration tests (5 new), architecture gates unchanged.

## S08-12 — The step input mapping: a downstream step reads exactly what its upstream produced (S08-12).

### What changed
The workflow graph contract (`contracts/workflow-graph/workflow-graph.json`) always described a node-level `input` map and `output` declarations, but the code dropped both on the floor — the parser read only `id`/`type`/`config`. They are now carried end to end:

- **`WorkflowNode`** (`workflowdefinition.domain`) gains `input` (`Map<String, Object>` — literal strings or `{node, output}` reference objects, verbatim) and `output` (`Map<String, String>` — declared output name to non-blank description), with javadoc anchored to the contract's `reference` `$def`.
- **`WorkflowGraphParser`** reads both fields with located type issues (`nodes[i].input`, `nodes[i].output.<name>`); wrong-typed values fail the parse gate before any domain object is produced.
- **`WorkflowGraphCodec`** round-trips both through the persisted JSONB, so an activated version keeps its wiring.
- **`WorkflowGraphValidator`** gains a **linkage gate** (`collectWiring`, after the cycle gate): it rejects a reference to an unknown node, a self-reference, a reference to an output the target node does not declare (including a target with no declared outputs at all), and a wiring value that is neither a literal string nor a well-formed `{node, output}` reference. Broken wiring can never reach a run — it is rejected before the version is persisted.

At execution time the worker resolves the wiring on the S08-11 seam, *before* the handler (and any tool) is invoked:

- **`StepInputMapper`** (`workflowexecution.domain`) — the pure engine. Literals pass through unchanged; a `{node, output}` reference resolves to the declared output's value in the referenced step's persisted output document. The lookup is exactly the declared output name — deliberately **no path navigation**, so the wiring can never reach into arbitrary fields of an upstream result (the "no access to arbitrary entity fields" rule). It re-validates the runtime facts the activation gate cannot see: the referenced document must exist and carry the declared name with a non-null value. Every rejection throws `InputMappingException` with a stable machine-readable `reason()` (`unknown-node`, `unknown-output`, `missing-output`, `null-output`, `invalid-literal`, `invalid-reference`); an `IllegalArgumentException`, so the S07-11 classifier maps it to `validation` — a permanent, classified contract failure recorded **before any call**, never retried.
- **`StepInputResolver`** (`workflowexecution.application`) — the application-edge seam that owns the text-to-tree JSON parsing: it parses **only** the upstream documents the wiring actually references (a node without wiring, or a wiring touching one output, never pays to parse the whole run's outputs), and a referenced document that is not well-formed JSON surfaces as `invalid-upstream-output`.
- **`StepExecutionContext`** gains `inputs()` (the resolved map, unmodifiable); `upstreamOutputs` stays for backward-compatible raw access. The pre-S08-12 constructor delegates with empty inputs, so existing handlers compile unchanged.

[`WorkflowWorker`](../../apps/agentflow-app/src/main/java/com/example/agentflow/workflowexecution/application/WorkflowWorker.java) resolves the wiring in `stepContext` — after the step enters `RUNNING`, before `StepHandler#handle` — so an unresolvable wiring is contained to the step exactly like a handler fault: classified, persisted on the fault transition, the run reconciled. The S08-11 readiness gate already guarantees the referenced predecessor completed (and in topological order the output is there); the mapper does not trust that, it re-checks (defense in depth).

No new cross-module compile edge: the mapper reads only the immutable `workflowdefinition` graph value objects the module's public API already hands across the `workflowexecution` boundary.

### Why
Until now a step's only inputs were its own `config` and the raw `upstreamOutputs` blob — every handler would have had to parse JSON and navigate maps by hand, with no contract about which names exist. The contract described the wiring; the platform now enforces it at two depths (activation + execution) and hands the handler a typed, resolved map. This is also the seam the `TOOL_CALL` handler consumes: its tool arguments can be wired from upstream outputs without the tool layer knowing about persistence.

### Verification
Unit, DB-free, no model/Kafka/system-clock dependency. `StepInputMapperTest` (13 tests): a node without wiring resolves empty; literals pass through; a reference resolves the declared output's value; a structured JSON value (a list of maps) is handed over whole — no navigation; every rejection carries its stable reason (`unknown-node`, `unknown-output`, `missing-output` for an absent document and for an absent name, `null-output`, `invalid-literal`, `invalid-reference` for a missing field and for an extra field); the resolved map is unmodifiable; null arguments throw. `StepInputResolverTest` (6 tests): the referenced document is parsed and resolved; a node without wiring parses nothing; an unreferenced (possibly legacy non-JSON) document is never parsed; a referenced document that is not well-formed JSON is rejected as `invalid-upstream-output`; a missing referenced document delegates to the mapper's `missing-output`; null arguments throw. `WorkflowGraphParserTest` gains a verbatim parse test and located issue paths for wrong-typed `input`/`output` fields; `WorkflowGraphValidatorTest` gains the linkage gate (accepts valid wiring and literals-only; rejects unknown node, self-reference, undeclared output, a target without declared outputs, and shape violations with their paths); `WorkflowGraphCodecTest` gains an input/output round-trip. `WorkflowWorkerTest` gains two recording-handler tests: resolved inputs (reference value + literal) reach the handler's `context.inputs()`; an unknown output path fails the step **before** the handler is invoked (recorded list empty), classified `validation` on the fault transition, the run reconciled to `FAILED`. `:apps:agentflow-app:check` green — compilation, all unit tests, spotless formatting, the OpenAPI contract gate and the architecture gates.

## S08-11 — The DAG readiness resolver: dependency resolution, failure/skip/cancel propagation and a deterministic execution order (S08-11).

### What changed
The [`DagReadinessResolver`](../../apps/agentflow-app/src/main/java/com/example/agentflow/workflowexecution/domain/DagReadinessResolver.java) (`workflowexecution.domain`) — the pure gate that owns the readiness decision the worker event loop had inlined since S07-08. Given the pinned graph and the already-persisted step states it resolves every `PENDING` step exactly once, into a `Resolution` of three ordered lists:

- **Ready** — every predecessor `SUCCEEDED` (a step with no predecessors is ready immediately). The list is ordered topologically: Kahn's algorithm with the free-choice tie broken by the node's declaration order in `WorkflowGraph.nodes()`. The resolution never iterates the input state map to build its output order, so the result is independent of the map's implementation or iteration order — the acceptance ("the order follows the graph edges and does not depend on the incidental ordering of collections") is a property of the algorithm, not of prose.
- **Skipped** — a predecessor `FAILED` or `SKIPPED` (the cascade is transitive: a decided outcome can never be retried into existence, so the dependent step can never run).
- **Cancelled** — a predecessor `CANCELLED` (S07-12 semantics: a step downstream of a drained predecessor can never observe the predecessor output it needs). A failure cascade takes precedence over cancel propagation — a decided failure classifies the step as `SKIPPED` even when another predecessor was cancelled.

Everything else — a predecessor still `RUNNING`, `READY`, `RETRY_WAIT` or `WAITING_FOR_APPROVAL`, or a step row not yet materialized — waits for the next pass; an absent row is never read as succeeded. A step in any non-`PENDING` state is never reconsidered (terminal states are absorbing, invariant 4). The propagation for failure/skip/cancel the plan asks for is exactly these three lists.

[`WorkflowWorker`](../../apps/agentflow-app/src/main/java/com/example/agentflow/workflowexecution/application/WorkflowWorker.java) now drives its per-pass decisions through the resolver: `executeUntilQuiesced` resolves once per pass and `applyResolution` records the cancels, then the cascade skips, then executes the ready steps **sequentially** in the resolver's topological order ("execute ready steps sequentially first" — a parallel executor is a later, measured change). Every transition still goes through the single transition service (invariant 4), and the readiness gate itself reads only persisted state — the graph is data, the decision is a pure function over it (invariant 7). The worker's inline `predecessors` / `hasFailedPredecessor` helpers are deleted; the cancel propagation they could not express is new behaviour, consistent with the S07-12 drain.

The resolver is pure — no Spring, persistence, time or randomness (invariant 10) — and defensive about its input: the activation validator rejects a cyclic graph and dangling edges before persistence, but the resolver never trusts its input, so a cycle's nodes are simply never emitted into the topological order (the run parks instead of executing out of order) and a dangling edge endpoint is ignored. No new cross-module compile edge: the resolver reads only the immutable `workflowdefinition` graph value objects the module's public API already hands across the `workflowexecution` boundary (the module-map arrow 15 edge the worker itself already uses).

### Why
S07-08 shipped the loop with the readiness logic inlined in the worker, as private helpers over the persisted step statuses. That worked, but the decision — the plan's S08-11 "dependency resolver" — was nowhere testable as a unit: the only evidence for the readiness gate, the cascade and the order was whole-worker tests, and the ordering guarantee ("follows the graph edges, not the incidental ordering of collections") was implicit in a loop that happened to scan the declaration order. Extracting the resolver makes the contract explicit and independently verifiable, and it is the seam S08-12 (step input mapping) and any future parallel executor build on: the resolver decides *what* may run and *in which order*; the worker only *runs* what it is given.

### Verification
Unit, DB-free, no model/Kafka/system-clock dependency. `DagReadinessResolverTest` (15 tests): a root is ready immediately; readiness needs *every* predecessor succeeded (the diamond's `d` waits for both `b` and `c`); the ready list's free-choice tie follows declaration order under a deliberately scrambled declaration (`[c, a, d, b]` resolves to `[c, b]` once `a` succeeded); the `Resolution` is value-equal across forward-inserted, reverse-inserted and `HashMap`-ordered state maps; a `FAILED` predecessor cascades the skip, a `SKIPPED` predecessor cascades it transitively through a chain, a `CANCELLED` predecessor propagates the cancellation, and a failure cascade wins over cancel propagation; a `RUNNING` / `RETRY_WAIT` / `WAITING_FOR_APPROVAL` predecessor keeps the step waiting; a missing predecessor row is never read as succeeded; a non-`PENDING` step is never reconsidered; a mixed graph classifies every pending step exactly once; a cycle never makes its nodes ready (an acyclic root outside the cycle is unaffected); a dangling edge endpoint is ignored; null arguments throw `IllegalArgumentException`; the resolution lists are unmodifiable. `WorkflowWorkerTest` gains a recording-handler test proving the worker executes a scrambled-declaration diamond (`[d, b, c, a]`, edges `a→b, a→c, b→d, c→d`) in the exact topological order `a, b, c, d`, and all pre-existing worker tests (chain, cascade-fail, diamond, transient/permanent fault classification, cancellation drain) pass unchanged against the resolver-driven loop. `:apps:agentflow-app:check` green — compilation, all unit tests, spotless formatting, the OpenAPI contract gate and the architecture gates; the change adds no cross-module compile edge (`workflowexecution` still compiles only against its own package plus `workflowdefinition` and `messaging`).

- `CHANGELOG.md` — added the S08-11 bullet under `Unreleased → Added` (newest-first).

### Follow-up

A parallel executor would consume the same `Resolution` — the determinism guarantee is what makes parallelism safe to reason about later.

## S08-10 — The bounded tool executor: per-tool timeout and global / per-tenant concurrency caps (S08-10).

### What changed
The [`BoundedToolExecutor`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/BoundedToolExecutor.java) (`toolexecution.application`) — the bounded executor every tool call runs through, completing the support vocabulary a previous change sketched in the same package (`ToolInvocation`, `ToolCallTimeout`, `ToolExecutionThrottleException`, `ToolExecutionError`). It enforces the two bounds the plan task names:

- **Per-tool timeout.** The bound is read from the call's own `ToolDescriptor#timeout()` (S08-01 made every descriptor carry a strictly positive timeout; the executor never invents one) and enforced by `ToolCallTimeout`: the call runs on the executor's pool and, when it does not answer within the bound, `future.cancel(true)` frees the pool thread — so a slow or hung tool can never occupy a worker indefinitely (the first half of the acceptance). `ToolCallTimeout` is the pure, pool-injected helper; the executor owns the admission and the error taxonomy around it.
- **Global / per-tenant concurrency caps.** A global `Semaphore` bounds the calls the whole process runs at once; a per-tenant `Semaphore`, keyed by the verified `ToolExecutionContext#tenantId()`, bounds what one tenant may occupy so a noisy tenant cannot starve the rest. Admission is `tryAcquire`, never blocking: a call beyond a cap is **rejected immediately** with `ToolExecutionThrottleException` carrying the stable reason `concurrency_limited` and `retryable() == true` — overload degrades into a controlled, classified outcome instead of an unbounded wait queue (the second half of the acceptance).

**The timeout outcome is ambiguous, never "cleanly failed".** Interrupting the pool thread frees the worker but does not undo a remote side effect the call may already have triggered — an external call is not exactly-once (invariant 6 / ADR-003). A timed-out call therefore surfaces as `ToolExecutionThrottleException` with reason `tool_timeout` and `retryable() == true`: the `TOOL_CALL` `StepHandler` (wired in S08-12) records an ambiguous attempt and retries with bounded backoff rather than declaring success or failure. The two halves are deliberate and documented on the class: the worker is freed (cancel), and the outcome is not lied about (ambiguous).

**Error taxonomy.** The executor introduces exactly its two bounded-outcome faults; a tool's own unchecked fault is unwrapped from the `ExecutionException` and rethrown unchanged so the caller classifies it with the tool's type (e.g. a `CalculationException`), while a checked fault is rewrapped in `ToolExecutionError` so it can cross the pool boundary (its cause preserves the original). An interrupted wait for the result restores the interrupt flag and reports through `ToolExecutionError` as well. Null arguments and non-positive caps throw `IllegalArgumentException` (the domain-guard convention, not `NullPointerException`).

**Capacity accounting.** Both permits release in a `finally` on every path — success, timeout, cap rejection and tool fault — so permits cannot leak and a burst of slow calls cannot permanently shrink the executor; a rejected call never acquires anything. The honest consequence of freeing the worker on timeout is documented: the orphaned pool task may still run after its permits are released — the accepted trade-off of bounding the worker (holding the permit until the task ends would let a hung remote call occupy a slot forever, which is the failure mode this task removes).

**Configuration, not magic numbers.** The pool size and both caps are bound under `agentflow.tools.executor.*` in `AgentFlowProperties.Tools.Executor` (`pool-size` 8, `global-max-concurrency` 32, `per-tenant-max-concurrency` 8, all Jakarta `@Min(1)` so a misconfigured bound fails startup) and surfaced in `application.yml`; `ToolExecutionConfiguration` builds the fixed `toolCallExecutor` pool (destroy method `shutdown`, so a context close stops the pool's threads without aborting a submitted call) and the `boundedToolExecutor` bean from them. The per-tool timeout itself stays part of each descriptor, not of this configuration. The executor is created in every profile — it is a plain value-bound object with no `DataSource`/Kafka dependency, safe in the DB-less skeleton (S01-02) and the `api` role; only the workflow-worker role drives calls through it.

### Why
S08-01…S08-09 defined the tool contract, the registry, the validators, the built-in tools, the call context and the invocation guard, but nothing bounded a call: a single hung tool could occupy a worker thread forever, and a tenant burst could exhaust the process with no controlled outcome. The plan task ("set a per-tool timeout; limit global/per-tenant concurrency; define safe behaviour on timeout, given that interrupt does not cancel a remote side effect automatically") is exactly these two mechanisms plus the honest timeout semantics, and the acceptance ("a tool does not occupy a worker infinitely; overload gives a controlled outcome") is a property of the executor, not of prose. The Spring wiring lands now (rather than in S08-12) because the caps are configuration values that must be validated at startup, and a misconfigured cap should fail boot before any tool runs.

### Verification
Unit, DB-free, no model/Kafka/system-clock dependency: `BoundedToolExecutorTest` (12 tests, all deterministic — slow calls sleep on the injected pool, blocking calls rendezvous on latches). A call within the bound returns its value; the descriptor timeout is honored (the same 300 ms call fails a 50 ms bound and completes under a 5 s bound); a timed-out call on a **single-thread** pool frees the worker — proven by a liveness probe with a hard 2-second `Future.get` bound — and reports `tool_timeout` with `retryable() == true`; permits are released after a timeout (the same tenant is admitted again); the global cap (1) rejects a second call with `concurrency_limited` while an in-flight latch-held call occupies the slot; the per-tenant cap (1) rejects a second same-tenant call while another tenant under the same global cap is still admitted; a rejected call consumes no capacity and later calls are admitted; a tool's unchecked fault is rethrown as the same instance; a checked fault arrives as `ToolExecutionError` with its cause; an interrupted wait restores the interrupt flag and reports `ToolExecutionError` caused by `InterruptedException`; null arguments and non-positive caps throw `IllegalArgumentException`. `:apps:agentflow-app:check` green — compilation, all unit tests, spotless formatting, the OpenAPI contract gate, and the architecture gates, confirmed active from the JUnit XML (`ArchitectureBoundaryTest`: `tests=1, skipped=0, failures=0`; `PackageDependencyGraphTest`: `tests=4, skipped=0, failures=0` — the change adds no cross-module compile edge: `toolexecution` still compiles only against its own package plus `agentcatalog`, `audit` and `workflowexecution`; the config wiring lives in the shared `config` package, the same pattern `workflowexecution` already uses for `AgentFlowProperties`).

## S08-08 — The tool execution context (S08-08).

### What changed
A minimal, tenant-scoped, immutable [`ToolExecutionContext`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/ToolExecutionContext.java) (`toolexecution.domain`) — the <em>call context</em> a tool is executed with. It carries exactly the slice a tool adapter must see and nothing that must not: the verified `tenantId`, the verified `actor`, the `runId` / `stepRunId` the call belongs to, the `correlationId` for tracing, and the `capabilities` (the minimal permission scopes the caller holds — read by the invocation permission guard, S08-09). It holds <b>no secret</b> — no JWT, API key, token, full prompt or document — which is the S08-08 rule ("do not hand out secrets to every tool adapter"). It is built <em>server-side</em> from the verified security context (HTTP) or the stored run re-checked against PostgreSQL (worker) — never from the Planner's arguments — and is an immutable value: the `capabilities` set is stored as an unmodifiable defensive copy and there are no mutators, so a model argument can never swap the actor or tenant the call runs as (the S08-08 acceptance). Canonical-constructor validation rejects a null tenant, run or capability set — the tenant is mandatory, a context with no tenant cannot scope a call (invariant 1) — while the actor, step and correlation label may be null (the correlation label defaults to the run at the wiring layer, per `CorrelationHeaders`). It reads no time, no randomness, no Spring or I/O, and depends on <em>no other module</em> (so the module boundary is unchanged: `toolexecution` still compiles only against `agentcatalog`, `audit` and `workflowexecution`). It is the calculator-layer mirror of `TenantContext` (`identity.application`), decomposed into its `tenantId` / `actor` primitives because `toolexecution` may not compile-depend on `identity` (the architecture gate, S02-08).

### Why
`BuiltInTools` seeds read-only tool descriptors (S08-02) and the pure executors exist (S08-05/06/07), but nothing yet threads the "who is calling, within what" context to a tool. The plan task ("pass tenant, actor, run, step, correlation ID and minimal capabilities; do not hand out secrets to every tool adapter") needs a single, explicit value for that — and the acceptance ("model arguments cannot replace the actor/tenant context") is a property of an immutable, server-side-built, validated value, not of prose. `ToolExecutionContext` is that value: it is the boundary the executor draws between the trusted security context (which decides who the call runs as) and the tool adapter (which must only see the minimal slice). It is placed in `domain` because it is a pure value (no Spring/I/O, reads neither time nor randomness, invariant 10), matching `ToolDescriptor` and the other `toolexecution.domain` values, and it is listed as a permitted public type of `toolexecution` in `docs/architecture/module-api.md` for the later `ToolExecutionService` / `StepHandler` wiring (S08-09 onward). The `capabilities` field is carried because the invocation permission guard (S08-09) re-checks scopes at call time; it is minimal — scope names only, never a token.

## S08-09 — The invocation policy guard (S08-09).

### What changed
A re-check of the permission immediately <em>before</em> the call, not only at workflow activation, as the `toolexecution.application` `@Service` [`ToolInvocationPolicy`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/ToolInvocationPolicy.java): right before a tool runs it resolves the tool <em>through the registry</em> (`ToolRegistry#resolve` — which tool, its {@link ToolDescriptor#riskClass()} and {@link ToolDescriptor#requiredScopes()}), and then checks the caller's <em>current</em> permission set (`ToolExecutionContext#capabilities()`) holds <em>every</em> required scope. The decision is returned as the immutable value [`PermissionDecision`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/PermissionDecision.java) carrying the machine-readable {@link ToolExecutionOutcome} (`ALLOWED` / `DENIED`) and a stable {@code reason()} (`allowed` / `missing_scope` / `unknown_tool`) plus the ordered {@code missingScopes()} the executor classifies with — so classification and logging need no string parsing. A call is `ALLOWED` only when the tool resolves <em>and</em> the current scopes cover the required ones; an unknown tool, an absent scope, or a capability set that lacks the side-effect scope is `DENIED`, and the guard fails safe with a `null` context for a scoped tool (a read-only tool needs no scope, so an empty set is "no side effect permitted", not "everything denied").

Supporting values:
- `ToolExecutionOutcome` — the invocation vocabulary (`ALLOWED` / `DENIED` / `EXECUTED`).
- `PermissionDecision` — the immutable decision: `outcome()`, `toolName()`, `reason()`, and `missingScopes()` (unmodifiable — an external caller cannot silently widen a decision).

It reads no time, no randomness, no Spring/I/O beyond the registry it wraps, and <b>adds no new cross-module compile import</b> — it reads the catalogue's risk class through `ToolDescriptor#riskClass()` (the catalogue-owned value already carried into the descriptor by S08-01), and its only non-`toolexecution` reference to `agentcatalog.domain.ToolRiskClass` is a Javadoc `{@link}`, not a compile edge — so the module boundary is unchanged (`toolexecution` still compiles only against `agentcatalog`, `audit` and `workflowexecution`).

### Why
`ToolExecutionContext` (S08-08) threads the caller's capabilities to a tool, but nothing yet re-checks them at call time — the plan task ("check the permission immediately before the call, not at activation; if a permission revoked after activation, block the call") needs exactly that. The acceptance is a property of re-checking the <em>current</em> permission set, not of trusting a check captured at activation: a permission granted at activation can be revoked by the time the executor runs the step, and the model must not be able to smuggle a capability through a stale check (invariant 7 / ADR-006 — the model is never an authorization authority, so the permission check is decided server-side from the verified context). `ToolInvocationPolicy` is the value that closes the loop: the registry (S08-02) is the owner of *which tools are registered and with what risk/scope*, and the guard reads those attributes **through** the registry rather than re-declaring them; the caller's capabilities come from the server-side-built `ToolExecutionContext` (never from the Planner's arguments). It lives in `application` (with `ToolRegistry`) rather than `domain` because it is a `@Service` that holds the registry, not a pure value, and it is the counterpart of `identity.application` permission checks.

## S08-02 — The deterministic tool registry (S08-02).

### What changed
An in-memory, deterministic [`ToolRegistry`](../../apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/ToolRegistry.java) (`toolexecution.application`), the single source of *which tools are registered*. A tool is therefore never callable unless it is registered.

Built around:
- `ToolRegistry` — `register(descriptor)`, `resolve(name, version)` → `Optional<ToolDescriptor>` (empty for an unknown pair), `containsTool`, `all()` (unmodifiable snapshot), `size`. - `ToolKey` — the package-private `(name, version)` value key (record). The dedup key is the pair the Planner references, **not** the descriptor `id` (which stays a stable unique identifier on the descriptor for audit/persistence).
- `DuplicateToolRegistrationException` — extends `IllegalStateException`; a startup/config error, thrown by `register` on a duplicate `(name, version)`.
- `BuiltInTools` — the factory that seeds `calculator` (S08-05) and `report` (S08-06) descriptors at startup.

### Why
The S08-02 plan task ("register adapters at startup; reject duplicate ID/version; forbid dynamic registration by the LLM/user; deterministic registry") had no implementation yet. This closes the acceptance criteria:
- **Unknown tool is never called.** `resolve` returns `Optional.empty()` for any pair never registered; the planner/permission layers treat that as "not callable", so an unknown or never-registered tool cannot be invoked.
- **Duplicate registration clearly breaks startup.** A duplicate `(name, version)` throws `DuplicateToolRegistrationException` *from the `@Bean` factory method*, so the Spring context fails to start — a mis-wired registry is a configuration error that is visible, not silently kept (one of two tools).
- **No dynamic registration by the LLM/user.** There is **no HTTP endpoint**; registration is a platform operation at startup only, an invariant (`AGENTS.md` "Forbidden": dynamic tool registration by the LLM or a user).
- **Recovery.** The registry is in-memory with no external dependency (no DB), so it is safe in every profile (API role, DB-less skeleton). It holds no secrets, no prompt, no `tenantId`/`runId`; its `all()` snapshot is metric/log-safe.

## S08-01 — The registered-tool contract (S08-01).


- **The registered-tool contract (S08-01).** The shape of a *registered tool* is now a typed, immutable value object, `ToolDescriptor`, in `toolexecution.domain` — the value that closes the loop between the tool allowlist (which tool/permission a run is allowed to use) and the executor (which runs it and how). A tool is only callable when it has a {@link ToolDescriptor#riskClass()} the caller is permitted to use, the caller holds every {@link ToolDescriptor#requiredScopes()} scope, and the call passes the {@link ToolDescriptor#inputSchema()} / {@link ToolDescriptor#outputSchema()} validation — none of which is inferred from the human-readable {@link ToolDescriptor#description()}. The `ToolDescriptor` is a `record` with value equality, so the registry can dedupe and cache it (S08-02), and its canonical-constructor validation guarantees an invalid descriptor can never reach a call (non-blank `id`/`name`/`version`, present schemas, present scopes/risk/retry, a strictly positive timeout).

- **`ToolRiskClass` — the tool's blast radius, owned by the catalogue.** The three-class enum (`READ_ONLY`, `WRITE`, `EXTERNAL_SIDE_EFFECT`) that classifies a tool by the change it can make to external state now lives in `agentcatalog.domain`, not `toolexecution.domain`. The catalogue is the *owner* of the tool allowlist and its risk taxonomy (module-map edge 3 / `docs/architecture/module-api.md`); keeping the risk model there is what lets the catalogue own "which tools exist and how risky they are" while `toolexecution` only *reads* a risk class the catalogue assigned. `toolexecution` depends on `agentcatalog` (edge 3) to carry `ToolRiskClass` into the `ToolDescriptor`, so the model is defined once, owned once, and never duplicated across the boundary. An unknown risk class is denied by default (`S11-01`, ADR-006): the executor trusts the catalogue's closed set, not the Planner.

- **`JsonSchema` — the machine-readable contract, held as an immutable value.** A tool's `inputSchema`/`outputSchema` are held as an immutable, dependency-free value `JsonSchema` (a `Map<String, Object>` root, defensively copied and made unmodifiable), not parsed or validated in the domain. The domain holds the *shape*; schema validation of call arguments happens at the application/persistence boundary (`S08-02`). It rejects a `null` root with `IllegalArgumentException` (a tool without a schema cannot be validated, so it is not registered) and is value-equal so two descriptors with identical schemas compare equal.

- **`RetryPolicy` — how a failed call is retried, owned by the executor.** The retry parameters (max attempts, base delay, multiplier, max delay, jitter) move to `toolexecution.domain.RetryPolicy` as the tool-layer's answer to "how do I retry a failed call" — the tool-level sibling of `workflowexecution.domain.RetryPolicy` (`S07-10`), which still drives a step's *workflow* retry. This is a value object (value equality, no dependencies), carrying the same reproducible, bounded backoff the workflow policy uses, plus the same injection seams so it is testable without the system clock or `Math.random` (invariant 10). It is owned by `toolexecution` because the tool registry decides a *tool's* retry policy; the workflow-level policy still lives in `workflowexecution`.

#### What changed
- `agentcatalog.domain.ToolRiskClass` (new) — the three-value enum (`READ_ONLY`, `WRITE`, `EXTERNAL_SIDE_EFFECT`); the blast-radius taxonomy owned by the catalogue.
- `agentcatalog.domain.ToolRiskClassTest` (new, unit, DB-free) — the enum has exactly the three canonical values and nothing else, and each risk class is reachable and named.
- `toolexecution.domain.RetryPolicy` (new) — the tool-level retry policy value object: value-equal, dependency-free, reproducible bounded backoff with injected jitter/time, `of(...)`/`ofDefaults()` factories, `delayMillisForAttempt(attemptsUsed)`, `isRetryAllowed`, `nextAttemptTime`, and value equality.
- `toolexecution.domain.RetryPolicyTest` (new, unit, DB-free) — the exponential backoff progression, the `maxDelay` cap, the constant-multiplier edge, jitter reproducibility over 6 × 500 real draws, `isRetryAllowed` bounded by `maxAttempts`, the out-of-range jitter rejection, `nextAttemptTime` from an injected instant, and every invalid-construction case.
- `toolexecution.domain.JsonSchema` (new) — an immutable value wrapping the JSON Schema draft 2020-12 root as a `Map<String, Object>`; defensive copy, unmodifiable root, `null` root rejected, value-equal.
- `toolexecution.domain.JsonSchemaTest` (new, unit, DB-free) — round-trip, unmodifiable root, mutation does not change the value, and `null` root rejection.
- `toolexecution.domain.ToolDescriptor` (new) — the registered-tool contract: the canonical `record` with validated constructor, the `of(...)` factory, `ofDefaults()`, and the non-mutating scopes copy.
- `toolexecution.domain.ToolDescriptorTest` (new, unit, DB-free) — the descriptor carries its schemas and risk class, refuses a blank identity / a null risk class / scopes / retry policy / non-positive timeout, a missing machine-readable schema is rejected, the allowed-scope set is copied (mutating the source set does not change the descriptor), and value equality holds.

#### Why
Before this task the only thing standing between the allowlist (S08-01's `toolexecution.tooling` work) and the executor was an implicit set of field names — nothing typed, validated, or shared, so the "which tools may a run use" decision could not be reasoned about or tested in isolation. `S08-01` makes that decision explicit as one contract. `ToolRiskClass` is owned by the catalogue because the catalogue owns the allowlist and its risk taxonomy (the module-map edge 3 boundary); moving the risk model into `agentcatalog` keeps it defined once, and `toolexecution` reads it through the permitted edge rather than re-declaring it. The description is deliberately *not* authorization: the Planner is an untrusted planner (ADR-006) that reads `description()` to pick a tool, but the permission check (`requiredScopes` + `riskClass`) is decided server-side from the verified permission context, and an empty scope set means "no side effect permitted regardless of the description" (invariant: the model is not an authorization authority). `JsonSchema` and `RetryPolicy` are held as immutable values (no schema-parsing or sleep in the domain) so they are comparable, cacheable, and testable with injected time and randomness (invariant 10), and the canonical-constructor validation keeps an invalid descriptor from ever reaching a call.
