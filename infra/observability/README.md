# `infra/observability/` — telemetry stack

The observability stack is `grafana/otel-lgtm` (the **L**oki-**G**rafana-**T**empo-**M**etrics all-in-one image, retired as a log/trace store) behind a standalone OpenTelemetry Collector ingress, plus the dedicated, repo-owned Prometheus (S13-05), Loki (S13-07) and Tempo (S13-08) services, brought up by the `observability` compose profile. Everything is configuration as code: the collector boots from `otel-collector/collector.yaml`, Prometheus from `prometheus/prometheus.yml`, Loki from `loki/loki.yaml` and Tempo from `tempo/tempo.yaml`, all mounted read-only, and there is nothing to set up by hand.

## Layout

| Path | Contents |
|---|---|
| `otel-collector/collector.yaml` | The standalone Collector (S13-04): OTLP ingress, memory limiter, redaction, batch, health check; exports logs to the dedicated Loki (S13-07), traces to the dedicated Tempo (S13-08) and metrics to the lgtm backend. |
| `prometheus/prometheus.yml` | The dedicated Prometheus (S13-05): scrape configs for the application (`/actuator/prometheus`, bearer token) and the Collector's own metrics (:8888); versioned scrape intervals. |
| `loki/loki.yaml` | The dedicated Loki (S13-07): single-binary config with the OTLP ingest and the label contract — only `service.name` / `deployment.environment` are index labels; everything else is per-entry structured metadata. |
| `tempo/tempo.yaml` | The dedicated Tempo (S13-08): single-binary config with the OTLP ingest, local blocks + WAL, 7-day block retention and the documented sampling policy. |
| `grafana/provisioning/` | Grafana provisioning as code (S13-06): datasources, the dashboard provider and alert rules, mounted read-only into the lgtm container. The alert rules (S13-06): the scrape-target-down rule; the S13-17 operational set adds seven rules (api-error-rate, db-saturation, outbox-age, kafka-lag, expired-leases, provider-failures, ingestion-failures) with threshold/for guard/severity/runbook_url. |
| `grafana/dashboards/` | Provisioned dashboards as JSON with stable UIDs; a manual UI edit is not a change. Currently: `agentflow-overview` (S13-06 smoke), `agentflow-api-jvm-db` (S13-14), `agentflow-workflow-kafka` (S13-15), `agentflow-ai-rag-cost` (S13-16). |

## Why lgtm backends behind a standalone collector

The standalone design (OpenTelemetry Collector → Prometheus + Loki + Tempo, each its own container) was not viable for the local stack *as backends* when it was chosen (S01-16): the Loki exporter was removed from `otel/opentelemetry-collector-contrib` (the 0.165 line ships only the deprecated receiver), so `grafana/otel-lgtm` — the Collector with the Loki exporter bundled, the officially recommended backend for local dev/demo — kept all three stores working in one image. Since then Loki 3.x gained **native OTLP** ingest (`/otlp/v1/logs`), and S13-07 uses exactly that: the dedicated Loki container replaces the exporter entirely — the collector posts logs with its `otlphttp` exporter and Loki's own `otlp_config` enforces the label contract. A production deployment would run these as separate services (deployment sprint).

Since S13-04 the **standalone contrib collector is the OTLP ingress**: the application exports to it (not directly into lgtm), so the ingress contract — memory limit, batching, attribute redaction, health check — is this repo's config, independent of the all-in-one image. Since S13-05 the dedicated **Prometheus is the repo-owned metrics store** and owns the host-published :9090; it scrapes the application's `/actuator/prometheus` endpoint (the S13-02 contract: metrics ship through the Prometheus scrape, never OTLP push) and the collector's self-metrics. Since S13-07 the dedicated **Loki is the repo-owned log store** and owns the host-published :3100: the collector's logs pipeline exports to its native OTLP endpoint, its `limits_config.otlp_config` keeps only `service.name` / `deployment.environment` as index labels (every other attribute lands in per-entry structured metadata — tenant/run/user/document IDs can never index-label a stream), and the 7-day retention matches the dedicated Prometheus. Since S13-08 the dedicated **Tempo is the repo-owned trace store** and owns the host-published :3200: the collector's traces pipeline exports to its OTLP/gRPC endpoint, and its `compactor` block retention matches the dedicated Prometheus and Loki. lgtm's bundled Loki and Tempo receive nothing — the collector no longer sends logs or traces there — and are retired as stores; lgtm still serves the **metrics** pipeline internally (its bundled collector receives the app-pushed OTLP metrics). Since S13-06 **Grafana is provisioned from Git** (datasources, dashboard provider, dashboards, alert rules mounted read-only from `grafana/`): the clean-start Grafana loads the AgentFlow datasource pointing at the dedicated Prometheus, the *AgentFlow / Overview*, *AgentFlow / API/JVM/DB* (S13-14), *AgentFlow / Workflow & Kafka* (S13-15) and *AgentFlow / AI/RAG/Cost* (S13-16) dashboards and the *AgentFlow scrape target down* alert with no manual setup, and the API refuses UI saves of provisioned dashboards. The Loki (S13-07) and Tempo (S13-08) datasource UIDs now point at their dedicated services — URL edits in Git, exactly the S13-06 promise; the remaining lgtm-internal datasource entries are declared in the same provisioning file.

## Endpoints (host-published)

| Port | Service | Purpose |
|---|---|---|
| `4317` / `4318` | otel-collector | OTLP (gRPC/HTTP) ingress — the only OTLP surface the app talks to |
| `13133` | otel-collector | `health_check` extension (smoke scripts / operator probes) |
| `9090` | prometheus | Prometheus UI / HTTP API — the repo-owned metrics store (debug; the Grafana datasource in S13-06) |
| `3000` | Grafana | dashboards; exposes Prometheus, Loki and Tempo as datasources |
| `3100` | loki | the dedicated Loki HTTP API — the repo-owned log store (debug; the Grafana Loki datasource in S13-06) |
| `3200` | tempo | the dedicated Tempo HTTP API — the repo-owned trace store (debug; the Grafana Tempo datasource in S13-06) |

## Configuration

- `otel-collector/collector.yaml` (this directory) is the standalone collector config: `otlp` receivers, `memory_limiter` (256 MiB ceiling, 64 MiB spike), `attributes/redaction` (drops body/prompt/document attributes — defense in depth; the app instrumentation never emits them, S13-03), `batch` (5 s / 8 192 / 16 384), `health_check` extension, a `prometheus` telemetry reader exposing the collector's own metrics on :8888 (scraped by the dedicated Prometheus over the observability network), and the exporters per pipeline — `otlp_http/loki` (logs, S13-07), `otlp_grpc/tempo` (traces, S13-08) and `otlp_grpc/lgtm` (metrics only — the dedicated Prometheus scrapes the app's `/actuator/prometheus` endpoint instead of receiving OTLP-pushed metrics, so the lgtm bundled collector only carries the app-pushed metrics). The image is pinned by digest in `infra/compose/docker-compose.yml`.
- Config validation: `docker run --rm -v <repo>/infra/observability/otel-collector/collector.yaml:/etc/otelcol-contrib/config.yaml:ro ghcr.io/open-telemetry/opentelemetry-collector-releases/opentelemetry-collector-contrib:<pinned> validate --config=/etc/otelcol-contrib/config.yaml` (also the compose healthcheck — the image is distroless, so the collector binary re-validates the mounted config; the runtime probe is the `health_check` extension on `:13133`).
- `prometheus/prometheus.yml` is the dedicated Prometheus config: 15 s scrape/evaluation intervals and two jobs — `agentflow-api` (the application's `/actuator/prometheus`, reached as `host.docker.internal:8080` from the container since the app runs on the host via `bootRun`; DOWN while the app is not running) and `otel-collector` (`otel-collector:8888`, internal network). Retention is versioned as compose command flags (`--storage.tsdb.retention.time=7d`, `--storage.tsdb.retention.size=2GB`) — Prometheus keeps retention a startup flag, not a config-file key. The image is pinned by multi-arch index digest; the TSDB persists on the `agentflow-prometheus` named volume, so a removed container comes back with its history.

- `loki/loki.yaml` is the dedicated Loki config (single-binary mode, TSDB schema v13 on filesystem storage): the native OTLP endpoint accepts the collector's posts, and `limits_config.otlp_config` is the label contract — `ignore_defaults: true` drops the 17-attribute default index-label list, `service.name` / `deployment.environment` stay index labels via explicit `index_label` rules, and every other resource/scope/log attribute falls back to per-entry **structured metadata** (unmatched attributes never become labels; Loki's fallback action is `structured_metadata`). Retention is a config-file key here (`limits_config.retention_period: 168h`, enforced by the compactor) matching the dedicated Prometheus. The image is pinned by multi-arch index digest; chunks and the TSDB index persist on the `agentflow-loki` named volume. The image is distroless, so the healthcheck re-validates the mounted config with the binary's own `-verify-config`. One display quirk worth knowing: Loki 3.x returns structured metadata **alongside** stream labels in query responses, so a `run_id`-shaped value visible next to a stream is per-entry metadata — the authoritative index label set is `/loki/api/v1/labels`.
- lgtm bundles its own component configs (`/otel-lgtm/`); this repo pins the image by digest so the bundled stack (Collector, Prometheus, Loki, Tempo, Grafana) is version-locked in one place. Data (Prometheus, Grafana) persists on the `agentflow-observability` named volume. Grafana's admin password defaults to a local-only value via `GF_SECURITY_ADMIN_PASSWORD` (override through a local `.env`).
- `tempo/tempo.yaml` is the dedicated Tempo config (single-binary mode, local blocks + WAL on the `agentflow-tempo` named volume — `/var/tempo/blocks` and `/var/tempo/wal`): the OTLP/gRPC + HTTP receivers (`0.0.0.0:4317` / `0.0.0.0:4318`; the otel-collector's traces exporter posts to :4317) and the compactor with a 7-day block retention (`compaction.block_retention: 168h`) — matching the dedicated Prometheus and Loki. The image is pinned by multi-arch index digest; the distroless image has no shell, so the healthcheck re-validates the mounted config with the binary's own `-config.verify=true` (the same pattern as Loki's `-verify-config`). **Sampling policy (S13-08):** this is a local, dev/demo stack and it keeps the app-side head-sampling contract of S13-03 — the application samples **100% of requests** (`management.tracing.sampling.probability: 1.0`, Boot's default is 10%), the collector adds **no** sampling processor, and Tempo stores everything it receives. The kubernetes profile is the only place that lowers the rate when volume demands it.
- `grafana/provisioning/` is Grafana's provisioning directory (mounted read-only at `/etc/grafana/provisioning`, selected and permitted through `GF_PATHS_PROVISIONING` / `GF_PATHS_PERMITTED_PROVISIONING_PATHS` — Grafana 13 rejects provisioning from unpermitted paths). `datasources/agentflow.yaml` declares **every** datasource of the stack: the dedicated `agentflow-prometheus` (`http://prometheus:9090`, the S13-05 store) plus the lgtm-internal Prometheus/Loki/Tempo/Pyroscope entries that Grafana 13 would otherwise auto-create — auto-creation stops the moment any datasource provisioning exists, so the whole set belongs in Git. UIDs are stable contracts. `dashboards/agentflow.yaml` wires `grafana/dashboards/` (mounted at `/etc/grafana/dashboards`) as the AgentFlow provider (`allowUiUpdates: false`, `disableDeletion: true`); `alerting/agentflow-alerts.yaml` declares the alert rules (each with a `for` guard, a severity label and a `runbook_url` annotation into `docs/runbooks/`): the S13-06 `agentflow-scrape-target-down` rule (and its `docs/runbooks/observability-scrape-target-down.md`) plus the S13-17 operational set — `agentflow-api-error-rate`, `agentflow-db-saturation`, `agentflow-outbox-age`, `agentflow-kafka-lag`, `agentflow-expired-leases`, `agentflow-provider-failures`, `agentflow-ingestion-failures` — each with an `OK` noDataState (silent on missing series, pages only on a real breach), an `Error` execErrState and a 5m/10m `for` guard. A manual UI edit of a provisioned dashboard or datasource is refused by the API — a change is a Git change.

## Scraping the application

`/actuator/prometheus` sits behind the default-deny secured chain (S13-02): a scrape must carry a bearer token. The token file is mounted at `/etc/prometheus/scrape/token` and is **git-ignored** (untracked since S13-14) — it is produced and consumed locally only, never committed. Mint a real one with the machine-to-machine client (S04-02):

```bash
bash scripts/mint-scrape-token.sh            # one token (~5 min of scraping)
bash scripts/mint-scrape-token.sh --watch    # refresh every 240 s for a session
```

Keycloak signs local access tokens for 300 s; Prometheus re-reads the token file before every scrape (verified on the pinned image), so the script only rewrites the file — no Prometheus reload or restart. After minting, `agentflow-api` comes UP on the next 15 s scrape. **Never commit the file with a real token** — it is git-ignored, and a fresh checkout never contains it; the mint script creates it on demand.
