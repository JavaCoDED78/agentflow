## Unreleased

### Added
- **The tool error matrix (S08-14): every error class a tool call can hit — unknown tool, denied permission, approval-required action, invalid input/output, timeout, transient (overload / flapping backend) and permanent tool fault — now has exactly one retry / state / audit result, pinned by one suite across the real call pipeline.** The component suites (`BoundedToolExecutorTest`, `ToolInvocationPolicyTest`, `ToolInvocationHistoryServiceTest`) prove each piece in isolation; the new `ToolErrorMatrixTest` (`toolexecution.application`) proves the matrix <em>across</em> the pieces, composed in the order the future `TOOL_CALL` `StepHandler` will drive them — invocation policy guard → input schema gate → bounded executor → output schema gate — with a policy denial told apart from a tool fault and the audit assertions driving the real `ToolInvocationHistoryService` against mocked repository/audit: a policy denial (unknown tool / missing scope) and a pre-call contract failure leave no history row and no audit record; a timeout is retryable and ambiguous (`TIMED_OUT`, audited for a started side-effect call because the effect may have completed); an overload rejection is retryable and never audited (`THROTTLED` — the call never started); a transient flap recovers within the retry bound while an exhausted one is terminal at it; a permanent tool fault keeps its own exception type (`FAULTED`, redacted stable token, audited). The matrix's **approval-required action** row closes a documented gap — [`ToolInvocationPolicy`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/ToolInvocationPolicy.java) gains the `missing_approval` precondition: an approval-gated tool (`ToolDescriptor.requiresHumanApproval()`) is refused on the automatic path (the taxonomy's `tool_policy_denial` — permanent, never retried, since a retry without a human decision cannot succeed), with a `decide(..., approvalGranted)` overload as the seam the human-approval lifecycle (S11) will feed once the approvals store exists. No new cross-module compile edge, no schema change — `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)

- **The durable tool invocation history (S08-13): an operator can determine which tool executed and how its call concluded — without ever seeing a secret.** Every call through [`BoundedToolExecutor`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/BoundedToolExecutor.java) now concludes in exactly one append-only metadata row in the new `tool_invocations` table (migration `V3_3_17`, owner `toolexecution`): the tool's `(name, version)` identity, the caller-supplied 1-based attempt number, the wall time the call occupied on an injectable monotonic clock, a bounded outcome class, and where the output lives. The outcome is a closed vocabulary — `SUCCEEDED`, `THROTTLED` (rejected under a concurrency cap, the call never started), `TIMED_OUT` (the ambiguous outcome: the side effect may have completed — invariant 6 / ADR-003), `FAULTED` — decided by the executor, never by the tool, and the record's `output_reference` is a `step-run:<step-id>` pointer to the owning checkpoint rather than the payload, so the payload keeps exactly one owner (`workflowexecution`). Redaction is structural, not a scrubbing pass: the table has no columns for arguments, output, prompt or document (invariant 8), and the failure slots carry only a stable machine-readable token (a throttle reason, or the faulting type plus its stable reason code) — never the exception message, which can quote a secret. Because the plan requires side-effect calls to be audited, the [`ToolInvocationHistoryService`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/ToolInvocationHistoryService.java) — the `ToolInvocationListener` seam the executor reports to — also appends an `audit_events` record (`AuditAction.INVOKE` / `AuditResourceType.TOOL`, actor `tool-executor`, redacted metadata `tool=<name>:<version>`) for every <em>started</em> call whose risk class is not `READ_ONLY`; a read-only call changes nothing, and a throttled call never started, so neither is audited. History is observability, not business state: a listener failure is logged and can never change the call's outcome, and without a database the executor degrades to that warning through the `NONE` fallback while the repository itself fails loud (`@ConditionalOnBean(DataSource.class)`, S01-02). 21 new DB-free unit tests (`BoundedToolExecutorTest` history section, `ToolInvocationHistoryServiceTest`, `ToolInvocationRecordTest`) plus a real-PostgreSQL `ToolInvocationRepositoryIT` (round-trip, append-order history, tenant-predicate isolation) and a sliced-context wiring test — `:apps:agentflow-app:check` and `integrationTest` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The step input mapping (S08-12): the DSL's `input` wiring now reaches a step's handler — a downstream step reads exactly what its upstream produced, and nothing else.** The workflow graph contract (`contracts/workflow-graph/workflow-graph.json`) always described a node-level `input` map (literal strings or `{node, output}` references to a predecessor's declared output) and `output` declarations, but the code dropped both on the floor: [`WorkflowNode`](apps/agentflow-app/src/main/java/com/example/agentflow/workflowdefinition/domain/WorkflowNode.java) now carries them, the [`WorkflowGraphParser`](apps/agentflow-app/src/main/java/com/example/agentflow/workflowdefinition/persistence/WorkflowGraphParser.java) reads them verbatim with located type issues, the [`WorkflowGraphCodec`](apps/agentflow-app/src/main/java/com/example/agentflow/workflowdefinition/persistence/WorkflowGraphCodec.java) round-trips them through the persisted JSONB, and the `WorkflowGraphValidator` gains a <b>linkage gate</b> that rejects — before a version is ever persisted — a reference to an unknown node, a self-reference, or a reference to an output the target node does not declare (the runtime mapper re-validates against the runtime facts as the second line of defense). At execution time the worker resolves the wiring on the S08-11 seam, <em>before</em> the handler (and any tool) is invoked: the pure [`StepInputMapper`](apps/agentflow-app/src/main/java/com/example/agentflow/workflowexecution/domain/StepInputMapper.java) (`workflowexecution.domain`) resolves literals unchanged and references against the completed predecessors' persisted output documents — looking up exactly the declared output name, with deliberately <b>no path navigation</b>, so the wiring can never reach into arbitrary fields of an upstream result — and the application-edge [`StepInputResolver`](apps/agentflow-app/src/main/java/com/example/agentflow/workflowexecution/application/StepInputResolver.java) owns the text-to-tree JSON parsing, paying to parse only the documents the wiring actually references. The resolved map lands in a new `StepExecutionContext#inputs()` field; `upstreamOutputs` stays for backward-compatible raw access. Every unresolvable wiring — an unknown node or undeclared output, a type violation, a null value, a referenced document that is not well-formed JSON — throws {@link InputMappingException}, an `IllegalArgumentException` the S07-11 classifier maps to `validation`: a permanent, classified contract failure the step records <b>before any call</b>, never retried and never reaching a tool. No new cross-module compile edge — the mapper reads only the immutable `workflowdefinition` graph value objects the module's public API already hands across. 13 DB-free unit tests (`StepInputMapperTest`: literals, reference resolution incl. structured JSON values handed over whole, every rejection reason with its stable code, unmodifiable result) + 6 (`StepInputResolverTest`: selective parsing, unparseable unreferenced documents tolerated, invalid referenced document rejected) + wiring/parser/codec/validator cases and two worker tests (resolved inputs reach the handler; an unknown output path fails the step before the handler and any tool, classified `validation`). `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The DAG readiness resolver (S08-11): a step is ready only after its predecessors succeeded, failure/skip/cancel propagate, and the execution order is deterministic — it follows the graph edges and never the incidental ordering of a collection.** The readiness decision the worker event loop made inline since S07-08 is now its own pure gate, [`DagReadinessResolver`](apps/agentflow-app/src/main/java/com/example/agentflow/workflowexecution/domain/DagReadinessResolver.java) (`workflowexecution.domain`): given the pinned graph and the already-persisted step states it resolves every `PENDING` step exactly once — <b>ready</b> when every predecessor `SUCCEEDED` (a step with no predecessors is ready immediately), <b>skipped</b> by a `FAILED`/`SKIPPED` predecessor (the cascade is transitive: a decided outcome can never be retried into existence), <b>cancelled</b> by a `CANCELLED` predecessor (S07-12 semantics — a step downstream of a drained predecessor can never observe the output it needs; a failure cascade takes precedence over cancel propagation), and otherwise left <b>waiting</b> for the next pass (a `RUNNING`/`RETRY_WAIT`/`WAITING_FOR_APPROVAL` predecessor, or a not-yet-materialized row — never read as succeeded). The `ready` list is ordered topologically (Kahn, free-choice ties broken by the node's declaration order) and the resolution never iterates the input state map to build its output, so the result is independent of the map's implementation or iteration order. Ready steps still run <em>sequentially</em> in this order — a parallel executor is a later, measured change. The resolver is pure (no Spring, persistence, time or randomness, invariant 10) and defensive about its input: a cyclic graph (rejected by the activation validator before persistence) or a dangling edge endpoint can never make a step ready out of order. [`WorkflowWorker`](apps/agentflow-app/src/main/java/com/example/agentflow/workflowexecution/application/WorkflowWorker.java) now drives its per-pass decisions, cascade skips and cancel transitions through the resolver and the single transition service (invariant 4); the inline predecessor helpers are gone. No new cross-module compile edge — the resolver reads only the immutable `workflowdefinition` graph value objects the module's public API already hands across. 15 DB-free unit tests (`DagReadinessResolverTest`) cover the readiness gate, all three propagations and their precedence, the determinism of the order under scrambled declaration and map iteration orders, and the defensive cycle/dangling-edge guards; `WorkflowWorkerTest` gains a recording-handler test proving the worker executes a scrambled-declaration diamond in exact topological order. `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The bounded tool executor (S08-10): a tool never occupies a worker indefinitely, and overload gives a controlled outcome.** Every tool call now runs through [`BoundedToolExecutor`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/application/BoundedToolExecutor.java) (`toolexecution.application`), which enforces the two bounds the plan requires: the call's own {@link ToolDescriptor#timeout()} — read from the descriptor S08-01 made carry it, never invented by the executor — frees the pool thread when the bound elapses ({@code future.cancel(true)} releases the worker even though the plan's caveat holds: <em>interrupting the thread does not undo a remote side effect</em>), and the global / per-tenant concurrency caps (a {@code Semaphore} per verified {@code ToolExecutionContext#tenantId()}, so one noisy tenant cannot starve the rest) reject overload <em>immediately</em> instead of growing a queue. A timeout is reported as {@code tool_timeout} and a cap rejection as {@code concurrency_limited} — both via {@link ToolExecutionThrottleException} with a stable machine-readable {@code reason()} and {@code retryable() == true}: the timeout outcome is deliberately <b>ambiguous</b> (the side effect may have completed — invariant 6 / ADR-003, never exactly-once), and a rejected call never started, so a later attempt with spare capacity is safe; the {@code TOOL_CALL} {@code StepHandler} (wired in S08-12) classifies both without parsing a message. The executor's own faults are exactly these two bounded outcomes; a tool's own unchecked fault is rethrown unchanged (classified with the tool's type) and a checked fault is rewrapped in {@link ToolExecutionError} so it can cross the pool boundary. Both permits release in a {@code finally} on every path — success, timeout, rejection and tool fault — so a burst of slow calls cannot permanently shrink the executor. The pool and the caps are configuration, not magic numbers: {@code agentflow.tools.executor.pool-size / global-max-concurrency / per-tenant-max-concurrency} (defaults 8 / 32 / 8, Jakarta-validated, in {@code AgentFlowProperties.Tools.Executor}) back the {@code boundedToolExecutor} + {@code toolCallExecutor} beans in {@code ToolExecutionConfiguration}; the per-tool timeout itself stays part of each descriptor, not of this configuration. 12 DB-free unit tests ({@code BoundedToolExecutorTest}): a call within the bound returns its value; a timed-out call frees the single worker thread (a hard-bounded liveness probe) and reports {@code tool_timeout} as retryable; permits survive a timeout without leaking; the global cap rejects with {@code concurrency_limited} while an in-flight call holds the slot; the per-tenant cap rejects a second same-tenant call while another tenant is still admitted; a rejected call consumes no capacity; a tool's unchecked fault is rethrown as the same instance, a checked fault arrives as {@code ToolExecutionError} with its cause; an interrupted wait restores the interrupt flag; null arguments and non-positive caps throw {@code IllegalArgumentException} — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The invocation policy guard (S08-09): re-check the permission <em>immediately before</em> the call, not only at workflow activation.** A tool is now authorized by {@link ToolInvocationPolicy} (`toolexecution.application`) — a {@code @Service} that, right before the call, re-verifies what the S08-02 registry already knew at registration (which tool, its risk class and required scopes) <em>and</em> what the caller holds <em>now</em> (its current permission scopes). It refuses to trust the check done at activation (invariant 7 / ADR-006: the model is never an authorization authority, and a permission can change between activation and invocation — the acceptance for S08-09). A call is {@link ToolExecutionOutcome#ALLOWED} only when the tool resolves <em>and</em> the current permission set holds every required scope; an unknown tool, an absent scope, or a capability set that lacks the side-effect scope is {@link ToolExecutionOutcome#DENIED} (a read-only tool needs no scope, so an empty set means "no side effect permitted", not "everything denied"); the guard fails safe with no context / a null-context scoped tool. The decision is returned as an immutable {@link PermissionDecision} carrying the machine-readable {@link ToolExecutionOutcome} and a stable {@code reason()} (`allowed`, `missing_scope`, `unknown_tool`) plus the ordered {@code missingScopes()}, so the executor classifies and logs without parsing a message. It reads no time, no randomness and no I/O, and <b>adds no new cross-module compile import</b> — it reads the catalogue's risk model through `ToolDescriptor#riskClass()` (the catalogue-owned value already carried into the descriptor by S08-01), and its only non-`toolexecution` reference to `agentcatalog.domain.ToolRiskClass` is a Javadoc `{@link}`, not a compile edge — so the module boundary is unchanged (`toolexecution` still compiles only against `agentcatalog`, `audit` and `workflowexecution`). 12 DB-free unit tests (`ToolInvocationPolicyTest`): allowed when the current capabilities hold every required scope, denied when a scope is absent, an extra capability does not change an allowed decision, an unknown tool is denied even when the caller holds every scope, an empty scope set allows a read-only tool, a null-context scoped tool is denied while its read-only sibling is allowed, <strong>a permission revoked after activation blocks the invocation</strong>, the guard re-checks current permissions and does not trust an activation decision, and the decision value object carries an empty/unmodifiable missing-scopes set. `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The tool execution context (S08-08): a minimal, tenant-scoped, immutable [`ToolExecutionContext`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/ToolExecutionContext.java) (`toolexecution.domain`) — the call context a tool is executed with.** It carries exactly the slice a tool adapter must see, and nothing that must not: the verified `tenantId`, the verified `actor`, the `runId` and `stepRunId` the call belongs to, the `correlationId` for tracing, and the `capabilities` (the minimal permission scopes the caller holds — used by the invocation permission guard); it holds **no secret** (no JWT, API key, token, full prompt or document). It is built <em>server-side</em> from the verified security context (HTTP) or the stored run re-checked against PostgreSQL (worker) — never from the Planner's arguments — and is an immutable value: the `capabilities` set is returned unmodifiable (defensively copied) and there are no mutators, so a model argument can never swap the actor or tenant the call runs as. Canonical-constructor validation rejects a null tenant, run or capability set (the tenant is mandatory — a context with no tenant cannot scope a call, invariant 1); the actor, step and correlation label may be null (the correlation label defaults to the run at the wiring layer). It reads no time, no randomness, no Spring or I/O, and depends on no other module (so the module boundary is unchanged — `toolexecution` still compiles only against `agentcatalog`, `audit` and `workflowexecution`), the calculator-layer mirror of `TenantContext`. 9 DB-free unit tests (`ToolExecutionContextTest`) covering all six fields, the null-tenant/run/capabilities rejection, the empty-capabilities (no-side-effect) case, the nullable actor/step/correlation fields, the unmodifiable capability set, the defensive copy, value equality, a reflection-based "no secret field" check and the "model cannot supplement the actor/tenant" property. `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The deterministic ticket lookup (S08-07): a pure, dependency-free [`TicketLookup`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/TicketLookup.java) (`toolexecution.domain`) implementing the demonstrative read-only `ticket.lookup` — it answers a ticket id against a fixed, in-memory fixture dataset and reproduces all three outcomes the plan asks for, without any external network: {@link TicketOutcome#NOT_FOUND} for an id absent from the fixture (answered deterministically, before any flap draw is consulted), {@link TicketOutcome#TRANSIENT_FAILURE} for a known ticket that flaps on every attempt (a transient fault, retried up to a bounded number of attempts so a retry can recover), and {@link TicketOutcome#SUCCESS} for the first clean attempt against a known ticket, returning the found {@link TicketRecord}. The one thing it reads — the per-attempt flap draw — is <em>injected</em> as a {@link java.util.function.Supplier<Double>} in {@code [0, 1)} (the same injection seam {@link RetryPolicy} uses for its jitter), so a fixed draw makes every outcome reproducible and the no-seam {@link #lookup(String)} entry point uses a shared {@link java.util.SplittableRandom} for realistic flapping in production. Holds its output as {@link TicketResult}; its fixture rows are {@link TicketRecord} and the two closed vocabularies are {@link TicketStatus} (OPEN/ON_HOLD/CLOSED) and {@link TicketOutcome} (the three outcome classes). It reads no time, no system randomness, no Spring or I/O (invariant 10). `BuiltInTools` seeds the read-only `ticket` descriptor (id `tool-ticket-lookup-1`, strict input/output JSON Schemas, `READ_ONLY`, a 5 s timeout, the default retry policy) and the registry seeds it at startup. 12 DB-free unit tests (`TicketLookupTest`) covering all three outcomes, a transient failure recovered after retries, the boundary draw, determinism, and every input guard (blank id, null source, {@code maxAttempts < 1}, an out-of-range draw). `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The report formatter (S08-06): a pure, dependency-free [`ReportFormatter`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/ReportFormatter.java) (`toolexecution.domain`) implementing the concrete `report.format` — it takes structured {@link StructuredFact}s and their {@link Citation}s and renders them into an HTML-escaped {@link ReportFormat#MARKDOWN} or {@link ReportFormat#JSON} report, capped at a fixed length. Every dynamic value is HTML-escaped in both formats (a hostile or prompt-injected fact can never become executable markup), and oversized input drops whole facts — flagged {@link ReportResult#truncated()} — so the output schema is stable for empty, valid and oversized inputs (the S08-06 acceptance). Holds its input as {@link ReportRequest} and its output as {@link ReportResult}; reads no time, no randomness, no Spring or I/O (invariant 10). 19 DB-free unit tests (`ReportFormatterTest`) covering empty/null/default input, valid Markdown and JSON (with citations and null URLs), HTML and ampersand escaping in both formats, and oversized truncation — `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The safe calculator evaluator (S08-05): a pure, dependency-free [`Calculator`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/Calculator.java) (`toolexecution.domain`) implementing the concrete `calculator.evaluate` — a self-contained recursive-descent operator-precedence parser over a closed numeric dialect (operands are typed {@link BigDecimal}s, exact and typed) built from {@code + - * /}, parentheses and decimal/scientific literals. It is an evaluator, never a general interpreter: there is no {@code eval}, no shell, no reflection, no class loading and no access to any language feature — an untrusted Planner cannot turn a calculator argument into code to run (invariant 7 / ADR-006). Addition, subtraction and multiplication are exact {@link BigDecimal} operations; division is bounded to 34 fractional digits half-up so {@code 1/3} is deterministic and {@code 10/4} is exact; a divide-by-zero throws, and every intermediate result is magnitude-bounded to {@code 1E1000} so numeric growth turns into a deterministic {@code overflow} rather than unbounded work. On the first problem it throws the new {@link CalculationException} carrying a stable {@code reason()} code (`invalid-token`, `empty-expression`, `division-by-zero`, `overflow`) so the executor classifies without parsing the message — the calculator-layer counterpart of {@link SchemaValidationException}; it reads no time, no randomness, no Spring or I/O (invariant 10). 29 DB-free unit tests (`CalculatorTest`) covering operator precedence, nested parentheses, unary signs, exact and scientific literals, division exactness and rounding, division-by-zero, overflow, and every malformed-input reason. `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The tool output-schema validator (S08-04): the very same dependency-free [`SchemaValidator`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/SchemaValidator.java) (`toolexecution.domain`) validates the tool's <em>result</em> against its machine-readable {@link ToolDescriptor#outputSchema()} — the same {@link JsonSchema} draft 2020-12 root held as an immutable `Map` tree — <em>after</em> the tool runs and <em>before</em> the step is marked SUCCEEDED, so a result that does not conform to the contract is never accepted, forwarded to the next step, or checkpointed** (the S08-04 acceptance criterion: "an invalid output is not marked as a successful step result"). It is the very same schema-agnostic engine that closes S08-03 — it validates any parsed value against any parsed schema — so the input and output gates share one implementation and one set of protective payload limits, a maximum node count and a maximum nesting depth (defaults `DEFAULT_MAX_NODES = 1_000`, `DEFAULT_MAX_DEPTH = 20`, tunable from configuration in S08-10). The engine distinguishes a <b>schema mismatch</b> — a produced result that fails the output schema, a deterministic contract failure — from a <b>transient execution error</b> the tool itself raises before producing a result (for example a provider timeout): the output gate only runs on a produced result, so a transient failure short-circuits on the tool call and is classified separately by the retry classifier. On the first violation it throws the same {@link SchemaValidationException} with the same stable `reason()` code (`type-mismatch`, `missing-required`, `unknown-property`, `payload-too-large`, `payload-too-deep`) the S08-03 engine uses, so the executor classifies the failure without parsing the message. It carries no JSON library dependency, no Spring or I/O, and reads neither time nor randomness, so it is a pure, testable value (invariant 10). 6 new DB-free unit tests (`SchemaValidatorTest`, now 27): a result matching its output schema is accepted; a type-mismatch, a missing required field, an unknown property in a strict output contract and an oversized result are all rejected before the step is marked succeeded, and a tool that fails transiently is reported as a transient error, not a schema mismatch. `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The tool input-schema validator (S08-03): a pure, dependency-free [`SchemaValidator`](apps/agentflow-app/src/main/java/com/example/agentflow/toolexecution/domain/SchemaValidator.java) (`toolexecution.domain`) that checks a parsed JSON value — the tool-call arguments — against the tool's machine-readable {@link ToolDescriptor#inputSchema()} (a {@link JsonSchema} draft 2020-12 root held as an immutable `Map` tree), blocking an invalid payload <em>before any tool side effect</em>. It validates the subset of JSON Schema a tool call needs: {@code type} matching for every JSON value type (object, string, integer, number, boolean, array, null — an {@code integer} schema accepts an integral value, including an integral double such as {@code 2.0}, but not a fractional {@code 2.5} or the string {@code "5"}), {@code required} fields, {@code properties} typing, {@code items} typing for arrays, and {@code additionalProperties: false} (the "strict contract" that rejects unknown properties; the default — absent or `true` — allows them), plus two protective payload limits, a maximum node count and a maximum nesting depth, so a hostile or malformed payload is rejected before it is processed. It is bound to a schema (via `SchemaValidator.of(JsonSchema)`) with injectable limits and conservative defaults (`DEFAULT_MAX_NODES = 1_000`, `DEFAULT_MAX_DEPTH = 20`); a production caller tunes the limits from configuration (S08-10). On the first violation it throws a {@link SchemaValidationException} carrying a stable `reason()` code (`type-mismatch`, `missing-required`, `unknown-property`, `payload-too-large`, `payload-too-deep`) so the executor can classify the failure without parsing the message. It carries no JSON library dependency — it walks the already-parsed `Map`/`List` tree, exactly as `JsonSchema` holds its schema as a parsed tree — no Spring or I/O, and reads neither time nor randomness, so it is a pure, testable value (invariant 10). 21 DB-free unit tests (`SchemaValidatorTest`: types, required, strict/non-strict unknown-property, array items, nested objects, node-count and depth limits with injected limits, the stable reason code, and a recording-executor test proving a valid input reaches the tool while an invalid one is blocked before the call); `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The deterministic tool registry (S08-02): an in-memory `ToolRegistry` (`toolexecution.application`) the platform seeds with its built-in tool descriptors at startup** — a single source of *which tools are registered*; the Planner chooses a tool through it, and every permission check reads a tool's risk class and required scopes through it, so a tool is never callable unless it is registered (unknown → `Optional.empty()` → never invoked, the S08-02 acceptance). Registration is platform-only and happens once at startup via the `toolRegistry` `@Bean` (`config/ToolRegistryConfiguration`), there is no HTTP endpoint, so dynamic registration by the LLM or a user is impossible (an invariant, `AGENTS.md` "Forbidden"). The registry deduplicates on the `(name, version)` pair — the identity the Planner references, not the descriptor `id` — and a duplicate registration throws `DuplicateToolRegistrationException` (a startup error) from the `@Bean` factory method, so the Spring context fails to start ("duplicate registration clearly breaks startup"); a concurrent duplicate is detected via atomic `putIfAbsent` rather than silently lost. The registry holds descriptors only (metadata); the executors are registered separately by name in the tasks that build them (S08-05, S08-06, S08-08). Seeded built-ins: the read-only `calculator` (S08-05) and `report` (S08-06). Built around three package-private helpers — `ToolKey` (the `(name, version)` value key, stays in the package), the `DuplicateToolRegistrationException` (extends `IllegalStateException`), and the `BuiltInTools` descriptor factory — plus 7 DB-free unit tests (`ToolRegistryTest`: resolve, unknown/wrong-version/blank-version unknown, dedup, two distinct versions, unmodifiable snapshot, null guard, concurrent registration of 16 distinct keys) and a lightweight Spring-context test (`ToolRegistryStartupTest`) proving the real config boots seeded and a duplicate registration fails context startup; `:apps:agentflow-app:check` green — [detailed](docs/devlog/sprint-08-tool-registry.md)
- **The registered-tool contract (S08-01): `ToolDescriptor` plus its value-objects** — the shape of a *registered tool* is now one typed, immutable `ToolDescriptor` (`toolexecution.domain`): the value that closes the loop between the tool allowlist and the executor. A tool is callable only when it has a risk class the caller may use, the caller holds every required scope, and the call passes the machine-readable input/output JSON Schema — none inferred from the human-readable `description()` (an untrusted planner, ADR-006; the model is never an authorization authority, an empty scope set means "no side effect permitted").
